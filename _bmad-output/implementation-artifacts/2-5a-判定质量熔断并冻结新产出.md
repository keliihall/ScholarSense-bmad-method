## Story

作为数据责任人，
我希望当受控质量资格事实确认某规则依赖已熔断时，立即锁存安全状态并建立唯一、可审计的质量异常任务，
以便错误数据不再继续扩散，既有事实及其独立业务状态保持可见，修复责任、影响范围和外部投递状态真实可追踪。

## 业务与交付价值

- 修复当前 Story 2.4 候选在后续健康事实到达时可能把 `fused` 直接重新计算为 `eligible` 的安全缺口；一旦进入熔断，必须等待 2.5b/2.5c 的受控恢复链路。
- 在 `ingestion-quality` 的同一 owner 事务中，把新产生的 fused 资格事实、审计、唯一 `RecoveryTask` 和公共任务 intent/outbox 一起持久化；外部平台不可用不削弱本地安全状态。
- 向 R6 展示失败来源/依赖、受影响规则/范围、当前质量异常任务和独立 `TaskDelivery.status`，避免把“待投递”误报为“已通知”或“已处理”。
- 为 Story 2.5b/c 的恢复生命周期、Story 3.2 的真实规则质量门和 Story 5.5 的公共任务最终 apply 提供稳定 handoff；本 Story 不提前声称生产环境已实现“零新产出”。
- 支撑 SM-9 与 NFR-10，但 2.5a 只交付 owner-local contributor evidence，不关闭其最终生产验收。

## Story 元数据与实施边界

- **硬依赖与开工基线：** Story 1.9 提供 PIC/DeliveryRecord 语义；Story 2.4 提供 RuleDependencyRegistry、严格事件排序和 `QualityEligibility`。当前 `main@017997a` 只合并到 Story 2.3，Story 2.4 是工作树中的已验证候选；实现前必须把其最终候选精确纳入 clean branch/commit，禁止按 HEAD 重建或覆盖用户现有改动。
- **单一事实 owner：** `ingestion-quality` 继续是 `QualityEligibility` 唯一写入者。2.5a 扩展 Story 2.4 的同一消费/事务路径以加入锁存与任务计划，不建立第二套 eligibility、quality fuse 或 rule runtime 真相。
- **锁存语义：** 新的、受控业务质量失败可令规则资格进入 `fused`；当前资格已经 `fused` 时，后续 passed/published dependency 只能更新证据，不能直接变回 `eligible`。`fused→recovering` 属 2.5b；`recovering→eligible`、失败回退和任务关闭属 2.5c。
- **触发语义：** 只有精确绑定 sealed batch、完成的质量判定、已批准图/profile/digest 的业务质量失败能创建熔断 episode/task。bootstrap `fused`、成员 version gap、missing、gap/backfill、poison、摘要/签名/合同不匹配或技术依赖故障不能伪装为阈值事故或追溯创建任务。
- **门槛复用：** 2.5a 不重算 QMDP/QSHM 或自由解释 `Q1/Q2`。它复用 Story 2.3 的公式/阈值/含边界比较证据及 Story 2.4 的组合结论；Task 0 必须把 QG 文本与现有 machine profile 的映射、滞回和可触发 reasonCode 冻结为受控 successor，冲突则 correct-course。
- **任务粒度默认决策：** Task 0 应冻结为“每个 `sourceId + dependencyId + active incident generation` 一个本地 `RecoveryTask`，聚合该 source owner 可见的受影响 RuleVersions”；episode 内后续失败批次更新原任务，2.5c 关闭后再熔断才分配新 generation。若受控 authority 要求别的 cardinality，必须在 Task 0 显式变更并用 fixtures/checker 锁定，不能只藏在代码里。
- **状态正交：** `QualityEligibility`、RuleVersion governance、RuleVersion runtime、Candidate/Clue 业务状态、任务业务状态与 `TaskDelivery` 分开保存。禁止把 `deliveryStatus` 加到 QualityEligibility，也禁止因熔断撤销规则批准、删除/隐藏既有 Candidate/Clue 或改写 DataBatch/QualitySnapshot。
- **权限边界：** 自动熔断由获准的质量 workload 触发；R6 数据责任人只读业务质量/任务并可在既有授权下发起受控 replay/reconcile，不能选择 `fused/eligible`。2.5a 不安装人工 pass、解除熔断或 recovery HTTP 端点；所有此类请求均保持 absent/deny。
- **公共集成边界：** PIC-1.0.0 没有 ingestion-quality producer、数据质量 route 或任务字段，且生产 `TaskDelivery` 尚不存在。必须发布 additive PIC/producer/route successor；不得把质量任务伪装成 `clue-care`、`care-work-item` 或 `report-job`，也不得复制 Story 1.9 的 test-scope reference adapter 作为生产框架。
- **冻结责任：** 2.5a 产生自足的 fused/freeze handoff 与 conformance evidence，但 `signal-evaluation` 的真实 consumer 由 Story 3.2 安装。未安装时 `runtimeEvidenceClaim=none`；fixture、outbox 行、HTTP 2xx 或 transport ack 都不是生产“零新 RuleEvaluation/Candidate/Clue”的证明。
- **外部验收边界：** FR-4/FR-59 的跨系统公共任务 apply、回写和最终生命周期仍归 Story 5.5；通用重试/对账最终套件归 2.7c。

### 本 Story 包含

1. 熔断锁存/episode/触发 reasonCode、任务 cardinality、PIC producer/route、投递和 retention 的 additive 合同、fixtures、digest locks 与 checker。
2. Story 2.4 processing state、transition policy 与 V16 successor transaction：当前资格/episode 加锁重读，原子提交 fused history/current、audit、eligibility outbox、`RecoveryTask`、任务 outbox 和幂等响应。
3. 独立 `TaskDelivery`/DeliveryRecord 的 pending/retrying/confirmed/failed 投影与有界 relay；外部 I/O 在事务提交后发生。
4. R6 source-owned 质量任务 list/detail 与现有质量面板只读表面；R7 技术投递/重试分面保持独立。
5. 合同、domain、MVC/JDBC、PostgreSQL 18.4、授权/隐私、PIC conformance、UI/a11y、性能和 additive release evidence。

### 本 Story 不包含

- 重新计算 QMDP/QSHM、修改历史 QualitySnapshot/hash、从 latest snapshot 补证据，或把 `impactScopeCodes` 当 dependency/rule/category。
- 新建另一套 QualityEligibility/fuse 状态机，跨模块直写 RuleVersion runtime，或创建 `RuleEvaluation`、`Candidate`、`Clue`。
- 2.5b 的 D4 `quality-fuse.recover`、样本重算、影响预览和 `fused→recovering`；2.5c 的观察窗、`recovering→eligible`、回退与任务关闭。
- 手工 fuse/pass/eligible/unfuse、移动端复杂质量表面、浏览器持久化业务对象或用 Toast 代替持久任务状态。
- 原位修改 V000015、PIC-1.0.0/旧 lock、release v1-v6、PAB/backend/frontend dependency locks，或顺手升级依赖。

## Acceptance Criteria

### AC-2.5a-CONTRACT：先消除单写入者、锁存策略与质量任务合同歧义（派生 readiness gate）

**Given** Story 2.4 已能在 verified assessed-failed 输入上发布 `QualityEligibility=fused`，但现有 evaluator 可在后续健康输入上重新算出 eligible，且 PIC-1.0.0 无质量任务 producer/route<br>
**When** Task 0 在编写 DDL、consumer、relay 或 UI 前生成受控 additive successor<br>
**Then** 合同唯一确定：QualityEligibility 单写入者、fuse transition/latch 表、可触发与不可触发 reasonCode、QG/QMDP/QSHM 映射、episode start/update/close/reopen、source-owner task cardinality、business/idempotency/workItem keys、affected-scope、PIC event/route/receipt、DeliveryRecord、retention/correction 和 2.5b/2.5c/3.2/5.5 handoff<br>
**And** 旧合同/lock 字节不变，schema/fixtures/checker 拒绝未知 Q1/Q2、未知 profile/digest、bootstrap/gap/poison 误触发、重复任务、跨 owner 泄漏和把 delivery/runtime 塞入 QualityEligibility；任何语义仍不唯一即 HALT/correct-course。

### AC-2.5a-HAPPY：锁存 fused 并原子建立唯一质量异常任务（受控原始 AC）

**Given** 场景门槛与依赖图已发布，获准 workload 收到 sealed、完整、严格绑定的业务质量失败，且该 `sourceId/dependencyId` 没有 active fuse episode<br>
**When** Story 2.4 的唯一 owner 事务应用受影响 RuleVersion 的 fused 决策<br>
**Then** 同一事务发布/保存 fused 事实与自足 freeze handoff，创建一个本地 `RecoveryTask` 及唯一公共质量任务 intent/outbox；受影响规则在后续 passed 输入到达时仍锁存在 fused，等待受控恢复<br>
**And** 既有事实/Candidate/Clue 保持可见且业务状态不变；R6 可见受影响规则/范围和独立 `TaskDelivery.status`。真实禁止新 RuleEvaluation/Candidate/Clue 的 apply 由 Story 3.2 验收，FR-4/FR-59 最终验收仍归 Story 5.5。

### AC-2.5a-AUTH-DENIAL：服务身份与人工动作失败关闭（受控原始 AC）

**Given** 调用方不是获准的数据质量 workload，或捕获后 authorization generation/capability/audience/mTLS/trusted-time 已失效<br>
**When** 尝试应用、伪造或解除 fused，或通过 replay/reconcile 绕过状态门<br>
**Then** 服务端拒绝，QualityEligibility、cursor、RecoveryTask、audit-success、outbox 和 TaskDelivery 均不发生业务变更<br>
**And** 只写最小拒绝审计（service/actor、action、result、policy/object version、traceId）；不记录学生、原始失败行或未授权成员。R6 页面不存在发布/解除按钮，recovery POST 继续 404/不暴露能力。

### AC-2.5a-ILLEGAL-STATE：未完成证据和未知合同不产生质量状态（受控原始 AC）

**Given** batch 未 sealed、质量判定未完成、assessed/published 配对非法、依赖图/profile/digest 缺失或不匹配，或输入属于 gap/poison/technical failure<br>
**When** 尝试把规则标记为 fused/eligible 或创建异常任务<br>
**Then** 拒绝/暂停/隔离且不发布可消费资格、不启动 episode/任务，cursor 按 Story 2.4 的 gap/poison 规则处理<br>
**And** DataBatch、QualitySnapshot、既有 QualityEligibility、RuleVersion governance/runtime 和既有业务对象保持不变；错误可诊断但不含学生明文。

### AC-2.5a-BOUNDARY：复用受控门槛证据而不重算（受控原始 AC）

**Given** 质量值恰等于已发布熔断阈值以及精确相邻上下样本<br>
**When** 通过 Story 2.3 QMDP/QSHM vector 和 Story 2.4 eligibility pipeline 执行判定<br>
**Then** 严格按 DEC-012 逐源合同、RuleVersion 引用的 `qualityGateVersion` 与 inclusive/exclusive 运算符得到唯一结果，2.5a 的 latch/task policy 只消费该结果而不重新实现公式<br>
**And** fused/task 保存精确 `batchId/snapshotId/hash`、source/dependency versions、formula/metric/threshold/operator/comparisonResult、QG/QMDP/QSHM 与 registry/RC versions+digests；未知 Q1/Q2 映射失败关闭而非猜测。

### AC-2.5a-DEPENDENCY-FAILURE：本地安全状态与外部投递解耦（受控原始 AC）

**Given** 公共质量任务/通知适配器、receipt 或目标平台不可用<br>
**When** 质量门判定为 fused<br>
**Then** fused history/current、local audit、eligibility outbox、RecoveryTask 与 public-task intent/outbox 仍在一个 owner-local 事务全成或全败，事务提交前不调用外部平台并立即保持冻结 handoff 可消费<br>
**And** 外部失败只令独立 `TaskDelivery.status=pending|retrying|failed`；`confirmed` 仅表示目标按合同确认投递，不表示任务受理、质量修复、恢复完成或 Story 3.2 已应用冻结。

### AC-2.5a-IDEMPOTENCY：重放复用原事实、episode 与任务（受控原始 AC）

**Given** 同一 `batchId + dependencyVersion + fuseBusinessKey`、同 payload/hash 和同 active episode 重放<br>
**When** 再次处理失败判定或 relay 重试<br>
**Then** 返回原 fused aggregateVersion、episodeId、RecoveryTask ID、workItemKey 和 TaskDelivery lineage，不新增 history/event/task/notification<br>
**And** 同键异 payload/digest 返回稳定 409；episode 内新失败批次只更新同一任务的影响/水位并保持 workItemKey，2.5c 终态关闭后新的业务失败才产生新 generation。

### AC-2.5a-CONCURRENCY：稳定锁序与陈旧写拒绝（受控原始 AC）

**Given** 判定期间 batch watermark、source/dependency version、registry graph、current eligibility、active episode 或授权 generation 变化<br>
**When** 旧 expectedAggregateVersion/routeSequence 提交结果<br>
**Then** 按稳定顺序锁 source/dependency→受影响 RuleVersions→episode/task，锁内重读全部当前状态，CAS 拒绝陈旧或混合版本写入，并由有界重试基于最新证据重算<br>
**And** 并发两个输入影响同一 episode 时最多产生一个 active task/workItemKey；不得死锁、部分推进或让某一 source owner 看见另一 owner 的成员。

### AC-2.5a-UPSTREAM-INTEGRITY：只接受 Story 2.4 的精确、自足证据（派生）

**Given** 一个 `QualityEligibility` 决策及其 Story 2.3/2.4 handoff<br>
**When** latch/task coordinator 决定是否创建或更新 episode<br>
**Then** 精确绑定 `eligibilityId/businessKey/aggregateVersion`、rule/version、完整 member set、registry/DCC/RC versions+digests、batch/source/dependency versions、snapshot/hash、QG/QMDP/QSHM versions+digests、lineage/watermark/effectiveAt 和 trigger reason<br>
**And** duplicate/old 幂等，gap 暂停补拉，poison 隔离；禁止 owner lookup latest、重算 profile/hash、按 UUID/occurredAt/watermark 猜顺序或把版本间隙当业务阈值失败。

### AC-2.5a-LATCH：质量状态不会绕过恢复策略自动解锁（派生）

**Given** 当前 RuleVersion 资格为 fused 或 recovering<br>
**When** 新 dependency composition 暂时全部 eligible，或新的失败再次到达<br>
**Then** `fused + pass → fused`，`fused + fail/replay → fused`，`recovering + pass → recovering`，`recovering + fail → fused`；只有从未进入 active fuse episode 的正常组合可以直接发布 eligible<br>
**And** transition 保存 prior/current evaluated state、reason、evidence version 和 episode identity；2.5a 不安装触发 recovering/eligible 的命令或适配器。

### AC-2.5a-QUALITY-TASK：本地任务、公共镜像和投递状态独立且唯一（派生）

**Given** 一个可触发的新 fuse episode<br>
**When** 创建或更新质量异常任务<br>
**Then** 使用 RFP 已定义的 `RecoveryTask` 作为 owner-local 业务对象，保存 opaque task/workItem identity、source/dependency、触发 batch/snapshot/profile、受影响 RuleVersions/授权范围、owner assignment、priority/dueAt、task status、current evidence/watermark 和 episode generation；公开事件使用 Task 0 锁定的 ingestion-quality producer/type/route<br>
**And** `TaskDelivery` 单独保存 target、routeSequence、attempt/receipt/status/lastErrorCode/nextAttemptAt，payload ≤64 KiB 且无 PII；任务业务状态不由 transport ack 改写，2.5a 不关闭任务。

### AC-2.5a-STATE-ORTHOGONALITY：历史事实与六类状态不互相污染（派生）

**Given** approved/inactive/fused RuleVersion、既有 Candidate/Clue、active RecoveryTask 和任意 TaskDelivery 状态并存<br>
**When** 发生熔断、重放、投递失败或查询<br>
**Then** governance、runtime、quality、Candidate/Clue business、RecoveryTask business 与 delivery 状态分别持久化和投影；fused 不撤销 approved、不删除/隐藏/迁移既有对象，delivery confirmed/failed 不改变 quality/task business state<br>
**And** `QualityEligibilityStatus` 不新增 delivery 枚举，`QualityEligibilityRecoveryCommandPort` 在 2.5a 继续无 inbound adapter，浏览器不能提交任何资格状态。

### AC-2.5a-UX：业务熔断、任务与技术投递诚实可见（派生）

**Given** 已授权 R6 在 desktop `data-quality-panel` 查看 source-owned 质量信息<br>
**When** 展开 fused 规则与质量异常任务<br>
**Then** 同屏显示失败 source/dependency、required/optional、operator/threshold、失败成员、受影响规则/范围、fused 时间/水位、RecoveryTask 与独立 TaskDelivery 文本状态；使用类似“门禁数据连续性未达门槛，相关规则已暂停产出”的具体业务语言，不显示成普通系统错误<br>
**And** pending/retrying 只写“待投递/重试中”，confirmed 只写“外部平台已确认投递”；文字/图标/颜色共同编码，loading/empty/filter-empty/error/forbidden/degraded 有单一真实 next step，恢复审批/观察/解除仍显示 unavailable 且无假按钮<br>
**And** WCAG 2.2 AA、键盘、读屏/live-region、200% zoom、1366/1440 通过；`<768px` 不渲染复杂面板，登出/换号/撤权/offline 清内存，无 localStorage/IndexedDB/CacheStorage/Service Worker 持久化。

### AC-2.5a-EVIDENCE：证据分层且 release 只做 additive successor（派生）

**Given** G-04、PAB、migration 和 release evidence 规则<br>
**When** Story 申请完成<br>
**Then** contract mutation、domain state matrix、MVC/JDBC、PostgreSQL 18.4 clean+upgrade/actual-login/raw-DML/rollback/concurrency、authorization/privacy、PIC relay/receipt、UI/a11y/performance 和 deterministic clean release replay 全绿<br>
**And** 动态分配全局下一 migration（Story 2.4 候选已占 V000015，预计 V000016），只做 forward/expand；发布当前 release successor（预计 v7），旧 V15/PIC locks/release v1-v6/PAB 字节不变，不新增依赖<br>
**And** evidence 分别标记 owner-local fuse/task/outbox conformance、public-task target activation、Story 3.2 consumer activation 和 Story 5.5 final apply；未安装部分保持 deferred/`runtimeEvidenceClaim=none`，不得把 fixture、DB 行、deployment profile 或 transport confirmation 冒充运行闭环。

### 技术与架构约束

- 遵循 modular monolith + hexagonal：domain 不 import Spring/JDBC/PIC adapter；`ingestion-quality` 只经 module API/events 与后续 `signal-evaluation`/public integration 交互，禁止跨模块表或内部类访问。
- 所有业务状态变化只经单一 application command/transition policy；幂等键、expected aggregateVersion、授权证据和完整 command body hash 一起校验。
- local fact/audit/outbox/task intent 同事务；DeliveryRecord/relay 独立推进。回调只更新自身 delivery sidecar，不回写 eligibility/task business status。
- 查询使用物化投影、覆盖索引和有界 bulk fetch；禁止按每条 rule/member/task N+1 hydration、在线扫描 QualitySnapshot 或每请求全表重算 digest。
- 事件/任务 payload 自足、≤64 KiB、`source+id` 唯一、aggregateVersion/routeSequence 单调；不依赖事件到达时再查“当前最新”owner 数据。
- API 继续使用 `/api/v1`、UUIDv7、ISO-8601 offset、OpenAPI 3.1.2、JSON Schema 2020-12、CloudEvents 1.0.2 和统一 error envelope。
- 审计、日志、metric、trace、DTO、DOM/a11y tree、task payload/error 不含 StudentRef、姓名、原始门禁行或高基数业务正文；affected scope 使用无 PII 的 source/dependency/rule/version 标识。
- 自动 fuse 不是高风险人工动作；不要套 HRAP/D4。D4 仅为 2.5b 恢复。
- 不新增 ORM、workflow engine、消息平台、前端状态/图表库；复用 Spring JDBC/`TransactionTemplate`、现有 outbox/inbox/lease/fencing 和 Vue Query 模式。
