## Story

作为集成团队，
我希望使用稳定、版本化且可重复验证的公共任务、消息与状态/结果回写契约，
以便后续质量、候选、线索、督办、转介和指标生产者可以安全接入学校既有公共能力，而不重复建设消息中心，也不把传输成功误报成业务已处理。

## 业务与交付价值

- 为后续真实生产者提供唯一的 `PIC-1.0.0` OpenAPI/CloudEvents/JSON Schema 契约、DeliveryRecord 语义、安全 profile、幂等/顺序/重试/对账规则和可执行 conformance suite。
- 固定“同一事项更新同一外部待办、升级只通知一次、终态关闭、失败可见但不阻塞本地业务”的公共边界，同时不提前实现 Candidate、Clue、TransferOrder、公共任务或指标领域。
- 把本地聚合 ID、外部 ID、eventId、aggregateVersion、水位和投递状态分开保存与解释，保证 transport accepted/confirmed、producer observed 与 consumer business applied 不被混为一谈。
- 用合成事件和受控沙箱验证失败、重复、乱序、崩溃恢复、认证和隐私负例，为 Story 2.5a/2.5c/2.7c、3.4/3.12、5.1/5.5 提供稳定入口；FR-4/FR-59 和 NFR-8 的最终运行验收仍归其 full owner。

## Acceptance Criteria

### AC-1.9-HAPPY：合成事件贯通公共适配器契约（受控原始 AC）

**Given** G-04、`PIC-1.0.0`、`TSP-1.0.0`、`MPP-1.0.0` 已批准，且学校目标系统管理的 non-production provider/consumer sandbox 可连接<br>
**When** 使用合成事件执行创建、更新、关闭、撤销、重试、乱序和双方 ID/水位对账<br>
**Then** 所有场景按锁定 OpenAPI/事件合同通过；同一事项更新同一 external task reference，每条 current DeliveryRecord 保存 `aggregateType + aggregateId + channel + contractVersion` 四元键、current generationKey/source aggregateVersion 与 mode-specific tagged provenance：stream=`route event + source fact + routeSequence`，intent=`deliveryIntentId + requestDigest`；local-external mapping 来自权威 generation ledger，状态仅为 `pending|retrying|confirmed|failed`<br>
**And** 非转介聚合不存在无归属 `deliveryStatus`，本 Story 不创建领域对象；服务间授权、失败可见、审计、幂等和 aggregateVersion 冲突路径均有自动化、可重复证据。

### AC-1.9-CONTRACT：PIC/TSP/MPP、版本与兼容性不可静默漂移

**Given** 构建、启动或 conformance runner 加载公共集成合同<br>
**When** 校验 OpenAPI 3.1.2、CloudEvents 1.0.2、JSON Schema 2020-12、PIC/TSP/MPP profile、adapter registry、fixtures 和 contract lock<br>
**Then** event type 精确满足 `scholarsense.<domain>.<aggregate>.<event>.v1`；strict CloudEvent 必含 `specversion/id/source/type/subject/time/datacontenttype/traceparent/data`，`id` 为 route projection 专属 UUIDv7，`source + id` 唯一，wire JSON 实际传输字节数 `<= 65,536`；data 必含 `schemaVersion/eventId/sourceFactId/sourceFactDigest/traceId/producer/aggregateType/aggregateId/aggregateVersion/channelId/routeSequence/contractVersion/correlationId/causationId/occurredAt/payload`<br>
**And** `sourceFactId` 是 source owner 为一次业务事实分配的稳定 UUIDv7，同一事实投影到不同 channel/schema/contractVersion 时保持不变；每个 route projection 必须获得不同 envelope/eventId，禁止跨 channel 复用 `source+id`。checker/application 同时强制：`data.eventId == envelope.id`；`time == occurredAt` 且均为 canonical UTC `Z`；`source == urn:scholarsense:<producer>` 且 owner 匹配；`subject == <aggregateType>/<opaque aggregateId>`；traceparent trace-id 等于 data.traceId；channelId 与当前 route descriptor 一致。冲突按 contract conflict 拒绝/quarantine<br>
**And** `aggregateVersion` 使用严格单调但可稀疏的 JSON safe integer、源聚合初始值 1；`routeSequence` 是每条 aggregate-stream route 连续的技术游标、初始值 1，route watermark 初始值 0；三者最大值均为 `9,007,199,254,740,991`，0/负数/溢出或 sequence 复用全部拒绝。`sourceFactDigest` 对 PIC 批准的、版本无关且已最小化/tokenized 的 source semantic fact 计算，输入明确排除 channelId/schemaVersion/contractVersion/routeSequence 和未批准敏感字段；同一 sourceFactId 的所有投影必须相同。`requestDigest` 对语义命令、`eventPayloadDigest` 对 route-specific event data snapshot 计算，三者均用 `SCHOLARSENSE-CANONICAL-JSON-1.0.0`。RFC 9530 `Content-Digest` 另对实际 HTTP body bytes 计算；四类 digest 命名、存储和比较不得混用。整个 identity-encoded UTF-8 body 必须 `<=65,536` bytes，PIC v1 只接受缺省/`identity` Content-Encoding<br>
**And** 同 major 只允许新增 optional 字段，删除/重命名/收窄/改变必填或状态语义必须升 major；但 envelope、安全和幂等控制字段始终 `additionalProperties=false`。event payload 按 adapter registry 中协商的精确 schemaVersion 投影：生产者只有在目标 consumer 声明支持后才能发送新增 optional 字段，旧 consumer 获得旧 schema 的 down-projected payload；不同投影允许 eventPayloadDigest 不同，但 sourceFactId/sourceFactDigest/providerEffect identity 必须相同。checker 覆盖 schema 元验证、引用闭包、四类 digest、跨 channel route eventId、版本协商/down-projection、未知键、错误版本、identity/compressed body、65,536/65,537 bytes、optional-addition 正例和 breaking-without-major 负例，禁止继续膨胀或改写现有通用 seed envelope。

Task 1 的 logical channel registry 必须覆盖公共 task、公共 message、状态/结果 writeback、外部 transfer work-order 和 metric publication 五类能力；具体 `channelId` 是该受控合同的输出，代码/fixture 在 lock 前不得自行硬编码名称。每个 `(channelId, contractMajor)` 精确绑定一个 `orderingMode=aggregate-stream|intent-command`；同一四元 lane 禁止混用两种 mode，需要不同 mode 就必须使用不同 logical channel，即使物理 endpoint 相同。provider endpoint/tenant/credential 是环境绑定而非合同枚举。每个 descriptor 必含 capability、channelId、contract/schema versions、owner/ownerStory、operations/events、consumer supported versions、orderingMode、sideEffectMode、SLO、authorization、signature/digest、failure/retry、reconciliation、sandbox class 和 contract-test binding；新增 channel 可作受控新增，改变既有 channel 语义必须升 major。

TSP/MPP 只作为版本化 lane profile 与适配器输入约束：urgent `2h` 接收/`24h` 反馈，normal `1` 工作日接收/`3` 工作日反馈，退回/待补充不重置时钟且只有批准 pause 可暂停；普通指标 `n>=10`、敏感/跨域 `n>=20`，低于阈值 suppression，百分比同时携带 numerator/denominator/metricVersion 并通过 anti-differencing 负例。本 Story 只验证 schema/adapter conformance，不创建 TransferOrder、业务时钟或指标计算器。

### AC-1.9-DELIVERY-OWNERSHIP：DeliveryRecord 是独立技术事实，不污染业务聚合

**Given** 任一合成聚合向某个 channel 发送一个或多个版本的命令/事实<br>
**When** 创建或推进 DeliveryRecord<br>
**Then** current DeliveryRecord 唯一键精确为 `aggregateType + aggregateId + channelId + contractVersion`，保存 latest/current pointer、`currentGenerationKey/currentDeliverySequence/status/fencingToken`、`lastConfirmedSourceAggregateVersion/lastConfirmedDeliverySequence/lastConfirmedGenerationKey` 及可重建的当前 mapping cache；generation mapping ledger 是 external mapping 唯一权威，cache 只能在同一事务 CAS 更新并由 ledger 重建。同键不因重试或新 intent 创建第二条 current record，两个 `lastConfirmed*` 口径不得缩写成有歧义的 `lastConfirmedVersion`<br>
**And** 输入接纳先创建独立、durable 的 `QueuedDelivery` identity（四元键+generationKey，尚无 deliverySequence），其 operation/priority/acceptedAt/tagged provenance 不可变，waiting/activated/superseded disposition 只写 append-only queue ledger。`provenanceMode=aggregate-stream` 时 `sourceEventId/sourceFactId/sourceFactDigest/eventPayloadDigest/channelId/routeSequence/sourceAggregateVersion` 全部必填且 intent fields 全部禁止；`provenanceMode=intent-command` 时 `deliveryIntentId/requestDigest/sourceAggregateVersion` 全部必填且 event/fact/route fields 全部禁止；both/none/mode 不匹配均在排队前拒绝<br>
**And** `generationKey` 为固定长度、无 PII 的 `g1.<base64url-no-pad(SHA-256(canonical-json))>`：event 输入精确为 `{"kind":"event","source":source,"sourceFactId":sourceFactId}`，因而同一 source fact 的 down-projection/cutover 不分裂副作用；intent 输入精确为 `{"kind":"intent","deliveryIntentId":deliveryIntentId}`。`deliveryIntentId` 精确为 `di1.<base64url-no-pad(SHA-256(canonical-json))>`，输入是 `{"kind":"message-intent","workItemKeyToken":tokenizedWorkItemKey,"notificationType":notificationType,"escalationVersion":escalationVersion}`；相同 digest 若绑定不同 canonical provenance 必须 security-conflict/quarantine，不能当 duplicate<br>
**And** 只有激活 QueuedDelivery 时才以 CAS 分配从 1 开始、最大 `9,007,199,254,740,991`、永不复用的 `deliverySequence` 并创建/替换 current generation，溢出 fail closed。current generation snapshot 在 sealed 前可用 CAS 更新；身份/provenance row 不可变，所有状态/授权 resolution/fence 变化写 append-only transition ledger，attempt 以“四元键+generationKey+attemptNo”标识。generation mapping facts 在“事项未终态期间 + 终态后至少 90 日 + RS hold（取最长）”窗口内 append-only 保留 `localGenerationId/externalTaskRef?/externalNotificationId?/providerReceiptDigest?/confirmedAt?`；task 稳定 lineage 与 message per-intent mapping 分字段/约束，current 轮转或重启不能丢失。外部 ID 一经绑定不得静默换值，`finalStatus` 从 ledger 重建并在 seal 时锁定；到期后清除 raw ID/receipt，只留 generationKey/providerLineageKey/tokenizedExternalRefDigest/finalStatus/hold tombstone，既防分叉又不承诺无限保留<br>
**And** 每四元键只允许一个 `pending|retrying` active generation。aggregate-stream 的普通候选按 routeSequence 派发；intent-command 按 acceptedAt+generationKey 派发；terminal 可按下述规则 supersede 较低候选。普通 candidate 只有在前一 generation confirmed，或 current failed 且已有受审计 `resolution=advance|reconcile` 时才能激活。`failed -> retrying` 仅允许 current、未 sealed、可恢复且有 remediation authorization 的 generation；一旦更高 deliverySequence 存在，旧 generation 永久 sealed，任何 worker/人工操作都不能恢复。每次 activate/claim/confirm/retry/fail CAS 都匹配四元键+generationKey+mode 对应 identity/digest+fencingToken<br>
**And** task/message 等关联 channel 共享 producer-owned/test-scope `SourceTerminalFence`，其 key 精确为 `tenant + aggregateType + tokenizedAggregateId + tokenizedWorkItemKey`、不含 channel/contractVersion/provider capability，因而能跨所有已登记 lane；记录 pending-gap/applied terminal version、event digest 和 fence epoch。它不是领域对象，也不进入 shared。terminal gap 一到即 hold 相关 intent；连续 terminal 的优先级高于普通 queue 和 lane cutover，无论 lane 为 active 或 draining 都不得进入普通 holding 等待<br>
**And** terminal 在 draining 到达时，单事务把 cutover 标为 `terminal-aborted`、取消 old+holding 的 message/ordinary candidates、停止未 claim retry、seal/fence 当前/在途 generation，并通过仍 active 的旧 contract lane 创建 terminal candidate+outbox；旧响应不能 confirm。terminal closed/reconciled 后该 lineage 才可从新的 shadow/drain 重新发起 cutover。普通 active lane 使用同一 cancel/fence/terminal-outbox 事务；enqueue、activate、claim、pre-send 都重检 SourceTerminalFence。PIC v1 不支持 reopen，terminal 后迟到/新 message intent 全部拒绝或隔离<br>
**And** 已在不可撤销网络 I/O 中的旧 attempt 只保留 history，晚到结果不能改 current；terminal tombstone/source version 与 reconciliation 保证外部最终关闭。create 尚无 externalTaskRef 时，target descriptor 必须声明 `terminalByStableWorkItemKey + rejectStaleSourceVersion`（或语义等价能力），否则不得声称可直接抢占，必须 fail closed/correct-course。接纳 candidate 时若无 active generation，则同事务 activate+outbox；普通 confirm 或受审计 advance 与“激活下一 candidate + 写下一 outbox”也同事务；terminal 的 cancel/fence/terminal candidate/outbox 同一事务。relay 启动和 reconciliation 另以同一 CAS promoter 恢复“sealed current + queued candidate”，关闭 confirm/promote、晚接纳和 preemption 的 commit 前后崩溃洞<br>
**And** task lifecycle 使用真实 source work-item aggregate identity。message intent-command 保留真实 source `aggregateType/id/version` 作为 provenance，但 `deliveryIntentId` 只是 sidecar 去重键，不是 CloudEvent aggregate、不是领域对象，也不替换 AD-24 owner。临期、超期和升级可在同一 source aggregateVersion 下成为不同 queued/generation history，current record 仍只有上述四元键且串行派发；同 intent 只有一个稳定 external notification mapping<br>
**And** task 的 `ProviderLineageMap` 以 `tenant + capabilityFamily + tokenizedWorkItemKey` 跨 contractVersion 唯一保存稳定 externalTaskRef；message 以跨版本稳定 deliveryIntentId 唯一保存 externalNotificationId。raw refs 与 generation mapping 使用同一“事项 active + terminal 后至少 90 日 + hold 取最长”窗口；到期时同事务清 raw refs/receipt，只保留 providerLineageKey/deliveryIntentId、tokenizedExternalRefDigest、terminal/final-status/hold tombstone。tombstone 使 day91 replay/restart/reconcile/cutover 都拒绝重新 create；它们属于 producer-owned/test-scope sidecar，不成为 shared 中心表<br>
**And** transport 失败只改变 DeliveryRecord/attempt/reconciliation evidence，不回退或推进源业务状态；reference adapter 不创建业务对象。生产 `shared/outbox` 最多增加 immutable `DeliveryRecordKey` 与 `DeliveryStatus`；所有 guarded transition、snapshot/entity/repository、queue/watermark/terminal fence、poison、HTTP/security/reconciliation 都留在 contract/test scope。未来 owner 在自己的 schema 保存实际 sidecar，禁止中心表和跨 schema 访问。

### AC-1.9-IDEMPOTENCY-CONCURRENCY：命令、事件和回调在重试/并发下至多生效一次

**Given** 相同或不同 workload 并发提交同一 `Idempotency-Key`、CloudEvent 或 aggregateVersion<br>
**When** 服务按 `tenant + actor/workload + commandType + Idempotency-Key` 和 canonical request digest 判断请求，并按 route event/source fact identity、digest 与 route watermark 判断事件<br>
**Then** 无 active generation 时，idempotency reservation、synthetic state、QueuedDelivery、activation/current DeliveryRecord、初始 outbox 和 completed original result 同事务提交；已有 active 时只提交 reservation+synthetic state+QueuedDelivery+completed result，不创建初始 DeliveryRecord/outbox，由后续原子 promoter 激活。事务外不存在已提交的“reserved 但业务未知”窗口。并发第二请求有界等待/锁定后只能读 completed result 或返回稳定 `IDEMPOTENCY_IN_PROGRESS + Retry-After`，绝不第二次执行；commit 后 response serialization/发送崩溃可恢复，rollback/owner 失联不遗留可夺取的半结果<br>
**And** idempotency result 从首次提交可信时间起至少保留完整 90 日（恰好 `createdAt + 90d` 仍可重放）；原 response 必须是隐私安全的 operation receipt，仅含 `operationReceiptId/idempotencyScopeToken/resultCode/acceptedAt/providerEffectKeyToken/traceId`，不含业务对象、字段、local/external ID 或当前状态。同一已认证 workload scope/key/同 payload 始终重放字节相同的原 receipt，不重新执行 object/purpose authorization，也不产生第二个业务/outbox/DeliveryRecord side effect；业务撤权由新高版本事实收敛，读取当前对象必须走另一个当前授权 query。无效/过期 workload identity 在查 key 前拒绝且不泄露是否存在；每次 replay/deny 写新的最小审计。同 key/不同 payload 返回稳定 409，跨 scope 相同 key 不碰撞<br>
**And** 上述“同 scope 重放原安全 receipt”只属于 inbound command idempotency。outbound `providerEffectKey` 精确由 `tenant + providerLineageKey + operationKind + generationKey` 生成，故跨 contractVersion 保持同一副作用身份；contractVersion 仍作为已签请求字段但不分裂 provider effect。relay 只重放已提交技术投递且不返回缓存业务对象，每次派发验证 current generationKey/lane/fence 和自身 workload identity，但不重新解释原用户权限，撤权/更正由新的高版本事实收敛。两个 idempotency plane 及 ProviderLineageMap 的 key、record、审计和测试必须分开命名<br>
**And** 超过 90 日按 RS-1.0.0 清除 stored response 和请求/payload material，只保留阻止 key/workItem lineage 分叉所需的最小 scope key、digest/hash、外部映射和保留/hold 元数据；清理后不得因新 eventId 或 key reuse 创建第二个 external task。全局删除/法定保留运行演练仍归 Story 6.6<br>
**And** 两个相同 expected aggregateVersion 的并发写者至多一个推进；失败者返回包含 currentVersion 的稳定 409，不产生混合 local/external ID 映射、重复 DeliveryRecord 或重复公共事项<br>
**And** 不同 eventId 若指向同一稳定 `workItemKey + provider create lineage` 也不能分叉为第二个外部事项；同一 deliveryIntentId 必须解析为同一 generationKey。provider 已接受但响应丢失、publish 后 confirm 前崩溃、callback technical inbox/mapping transaction commit 后 HTTP ack 前崩溃时，使用相同 outbound generationKey 安全重试。不允许“exactly once”虚假声明，证据必须证明 at-least-once transport + idempotent effect。

### AC-1.9-ORDERING-RECONCILIATION：重复、旧版、gap、poison 与双 ID 可恢复

**Given** 同一 aggregate-stream route 的事件/回调以 duplicate、stale、`routeWatermark+1`、gap、冲突摘要或 poison payload 到达<br>
**When** reference consumer 执行顺序判定和增量/全量对账<br>
**Then** inbox/watermark route key 精确为 `tenant + source + aggregateType + aggregateId + channelId + contractMajor`，其中 contractMajor 从完整 contractVersion 解析，同 major 的 schema minor/patch 协商不新开水位。`routeSequence` 是该 key 内连续游标；同 `source+eventId` 且同 eventPayloadDigest 才是 wire duplicate，不同 digest 是 security/contract conflict；同 `source+sourceFactId` 必须有相同 sourceFactDigest，不同则 conflict。相同 routeSequence+同 route event/digest 是 duplicate，相同 sequence 但 identity/digest 不同是 conflict；新 sequence 的 sourceAggregateVersion 必须严格大于 lastAppliedSourceAggregateVersion，但允许业务版本稀疏跳号。跨 schema/contract projection 用 sourceFactId+sourceFactDigest+generationKey 识别同一 effect，不要求 wire digest 相等。冲突全部 quarantine，只有 tagged provenance/digest 一致的 stale 才忽略且不回退<br>
**And** 新 route 处理首条事件前必须二选一：从 routeSequence=1 full replay；或由 source owner 原子登记可信 bootstrap checkpoint（`baselineSourceAggregateVersion/sourceOutboxPosition/snapshotDigest/authorityRef/createdAt`）后让首条 relevant event 使用 routeSequence=1。新聚合 checkpoint baseline=0；既有聚合、新 channel 或新 major 无 checkpoint/full replay 时 fail closed，不把首条 sourceAggregateVersion=N 误当 gap 或偷偷设水位。checker/test 覆盖 sparse `1,4,9` source versions、首条 N>1、新 channel 和 major cutover<br>
**And** 只有 route 的 `routeWatermark+1` 可进入 technical inbox/QueuedDelivery，且 inbox+watermark+queue 同事务；routeSequence gap 暂停该 route、触发 backfill/reconcile，补齐后按序恢复。channel A 的 gap 不阻塞 channel B，不同 contractMajor 各有 bootstrap/watermark，unrelated route 继续。poison 进入可见 quarantine/DLQ；更正/撤销必须是带更高 sourceAggregateVersion、连续 routeSequence 并引用 lineage/superseded event 的新事实，禁止原位改写已发布事件<br>
**And** 每个 `provider lineage + capabilityFamily` 跨 contractVersion 恰有一个 `sideEffectMode=active` lane；`shadow-no-side-effect` 只在按完整 contractVersion 隔离的 ShadowRouteEvaluation 中做 conformance，不改 active inbox/watermark、不创建 DeliveryRecord/outbox、不调用 provider。PIC v1 的 side-effect cutover/holding/abort/rollback 仅允许同一 contractMajor；新 major 可用独立 route+trusted checkpoint 做 shadow conformance，但 activation 必须经 correct-course/PIC successor 定义 forward migration，reference adapter 对跨-major cutover fail closed，不尝试 down-project holding<br>
**And** same-major cutover 状态机固定为 `active -> draining -> switched`：进入 draining 原子旋转 LaneCutoverFence epoch，新 admission 在匹配 epoch 下只写 lane-neutral `CutoverHoldingDelivery`（保留同 sourceFactId/generationKey/providerEffectKey），旧 lane drain 已有 queued/current；queued/pending/retrying/in-flight=0、lost-response 已 reconcile、failed 有 resolution 后，switch 事务 seal 旧 lane、复用 ProviderLineageMap/externalTaskRef、激活新完整 contractVersion、继承 route watermark 并按原顺序释放 holding。admission、inbox+watermark+holding、activate、promoter、claim、pre-send、confirm 都 CAS lane epoch，旧 epoch 永远不能提交<br>
**And** draining 可原子 abort 回 active 并把 holding 释放回旧 lane；switched 后仅在新 lane 尚无 claimed/provider effect 且所有新 outbox 未 claim 时允许原子 rollback，否则只能 forward-fix/PIC successor。terminal 使用上述更高优先级的 `terminal-aborted` 分支；providerEffectKey/deliveryIntentId 跨版本稳定，switch/abort/允许的 rollback 必须 no-loss/no-duplicate<br>
**And** 每 15 分钟增量、每日全量的确定性 job trigger/runner 能发现缺失/错配 generation-local external ID/receipt、外部 orphan、ProviderLineageMap 差异、状态差异和 routeSequence gap，记录 from/to route watermark、from/to sourceAggregateVersion、修复/未修复原因与 traceId；失败可重跑、job lease/fencing 防止双主提交<br>
**And** sourceVersion=1 create/update 未 claim、正在 retry 或已在途时若连续 routeSequence 的 sourceVersion=2 close/revoke 提交，跨 channel terminal fence 立即停止未发送/可取消旧工作；在途 worker 被新 fence 隔离，terminal generation 优先确定性派发。PG+HTTP 场景必须覆盖“旧 claim 阻塞网络→terminal 事务提交→旧响应/confirm 晚到→进程重启/对账”，断言旧 fence 不能改 current、terminal outbox durable、消息 channel 无迟到通知且 provider 最终 closed<br>
**And** transport ack、HTTP 2xx 和 sandbox provider confirmation 只可推进 synthetic DeliveryRecord；不得创建真实 public-task apply record 或推进其 consumer watermark。真实 apply 只在未来 owner 的本地业务事务成功后发生。

### AC-1.9-RETRY-FAILURE：事务 outbox、退避、DLQ 与失败可见

**Given** timeout、断连、429、5xx、4xx 合同拒绝、认证失败、意外 207/mixed acknowledgement、relay 崩溃或 lease 过期<br>
**When** synthetic producer 在同一 PostgreSQL 事务写入合成状态与 QueuedDelivery，并仅在无 active generation 时同时 activate current DeliveryRecord+outbox，reference relay 执行 claim → publish → confirm/retry/fail<br>
**Then** 事务 rollback 后该分支所有写入均不存在；commit 后 queued 或 active+outbox 都可从崩溃恢复。claim 使用 lease、attemptNo、fencingToken 和 `FOR UPDATE SKIP LOCKED`/等价安全语义；过期 worker 不能 confirm 新 owner 的 attempt<br>
**And** timeout/connect/429/5xx 按锁定的有上限指数退避+jitter 重试，超过预算进入可见 failed/DLQ；非重试合同/认证拒绝 fail closed 并告警；失败响应、日志和审计只含稳定低基数 code/trace，不回显 body、凭据、学生信息或签名材料<br>
**And** PIC v1 每请求只允许一个 operation generation；207、batch 或 mixed per-item ack 一律视为 unsupported contract response，整个 generation 不得 confirmed，进入 failed/reconciliation，而不是重试其中一部分。外部失败不阻塞本地业务提交，不显示“已处理/已送达”；只有合同定义的单项 provider acknowledgement 可将 synthetic DeliveryRecord 置 confirmed，且该确认仍不是业务 apply 证据。

### AC-1.9-SECURITY：mTLS、工作负载身份、签名与防重放 fail closed

**Given** 受控 outbound 请求携带 mTLS、短期 workload identity 与 `Content-Digest`，inbound callback 还携带 timestamp、nonce 与 message signature<br>
**When** adapter 在解析 JSON 或调用业务端口前，以有界原始字节验证该方向所需的 TLS peer、audience/scope、合同版本与实际接收字节 digest；callback 再验证签名覆盖字段、±5 分钟可信时间窗和 nonce 一次性<br>
**Then** approved security profile 必须分别机器冻结 outbound 的 mTLS/JWT/body-digest 规则和 callback 的 mTLS/JWT/body-digest/message-signature 规则；callback profile 固定 signature label、covered component 精确顺序、parameters/algorithm、timestamp/nonce headers，workload profile 固定 token format/claims/TTL/key rotation 与 mTLS identity binding，任一方向缺少其 required control 即拒绝<br>
**And** 本 Story 在 `PIC-SEC-1.0.0` implementation binding 中对所有有 body 的请求固定 RFC 9530 header `Content-Digest: sha-256=:<base64 digest>:`；只对 callback 固定 RFC 9421 label=`sig1`，covered component 顺序为 `"@method" "@authority" "@path" "@query" "content-digest" "content-type" "x-scholarsense-contract-version" "x-scholarsense-callback-timestamp" "x-scholarsense-callback-nonce"`，signature parameters 依次为 `created/expires/nonce/keyid/alg/tag`，`expires=created+300s`、`alg="ed25519"`、`tag="scholarsense-pic-callback-v1"`，header timestamp=created，header nonce=signature nonce<br>
**And** workload binding 为短寿命签名 JWT：protected header `typ="at+jwt"`、`alg="EdDSA"`、非空 `kid`，claims 含 `iss/sub/aud/scope/iat/nbf/exp/jti/cnf.x5t#S256`，`exp-iat<=300s`、leeway `<=60s`，audience/scope 匹配 descriptor，`cnf` 绑定当前 mTLS certificate thumbprint；issuer keys/truststore 从环境 port 轮换并允许 current+明确 overlap key<br>
**And** 以上 wire 值是本 Story 为使 PIC 可执行而增加的 implementation detail，不伪称为委托基线原文；runtime profile 必须引用既有 authorityRef/source digest，actual target capability digest 只由受保护 handoff 提供并在运行时匹配。目标 sandbox 不兼容时必须 correct-course 发布 PIC/profile successor 或明确修订 binding，不能静默在同版本换算法/token format；未知 issuer/kid/algorithm/profile、错误 audience/scope、未绑定证书、过期或尚未生效全部 fail closed，仓库不含生产 key/secret<br>
**And** durable callback inbox 以 `source+eventId+canonical payload digest` 幂等，nonce guard 以 `workload sub + keyid + nonce + contractVersion` 原子首次占用并至少保留 10 分钟。同 nonce 重放返回 409 且零技术状态变化；HTTP ack 丢失后的合法 retry 必须使用新 timestamp/nonce/signature 但保留同一 callback identity，新 nonce+同 event/digest 返回已提交 technical result。callback inbox/result 与 synthetic mapping/DeliveryRecord 更新同事务提交<br>
**And** 应用层错误固定为：401=缺失/无效/过期 identity 或 signature，403=audience/scope/certificate binding denied，409=nonce replay/idempotency/version conflict，422=contract/schema/digest/unsupported content invalid；每个进入应用的拒绝写最小审计且不写成功状态。mTLS 握手失败发生在 HTTP/应用之前，没有 HTTP 状态或 LocalAuditFact，只产生不含证书主体/secret 的 TLS 层安全日志与低基数 metric<br>
**And** 双向 TLS 沙箱覆盖正常握手、无 client cert、错误 CA/hostname、过期证书和禁止 redirect；共享 `HttpClient`/等价客户端显式配置 SSLContext、connect/request timeout、no-redirect 和受控连接复用，不为每次重试新建客户端。测试固定证书/key 明确标记 non-production。

### AC-1.9-LIFECYCLE-PRIVACY：同一事项、最小字段、撤销/关闭与消息唯一

**Given** 合成 work item 产生 create、owner/priority/due/progress update、due/overdue/escalation、terminal/withdraw/merge/revoke 和最小结果回写<br>
**When** 公共适配器构造请求并接收回执<br>
**Then** 同一 `workItemKey` 始终复用同一 external task reference；终态/withdraw/revoke 关闭原事项，merge 源事项关闭并只保留 opaque redirect；重复通知键 `workItemKey + notificationType + escalationVersion` 唯一，一次升级不会重复发送<br>
**And** task DTO 的批准字段只含 `workItemKey/operation/itemType/ownerRef/priority/dueAt/progressState/taskStatus/deepLinkRouteId/routeState` 及公共 envelope 字段，其中 operation、priority、progressState、taskStatus 都是 PIC 锁定枚举；message 另只含 `notificationType/escalationVersion`，回写只含本地 aggregate ID/version、eventId、status、occurredAt、resultCategory、trace/correlation/causation ID 和 contract version。outbound DTO 根本不构造自由文本、证据正文、学生原始标识、token、联系方式或网络内容；inbound 对未协商字段按 strict schema 拒绝，不以“收到后再删字段”作为权限边界<br>
**And** deep link 只能由服务端根据 approved `deepLinkRouteId + opaque routeState` 生成同源相对路径；合同锁定 route/origin allowlist、单次 canonical percent-encoding 和最大长度，拒绝 user-supplied absolute URL、外部 origin、userinfo、fragment、CRLF、双重编码、`javascript:`/`data:` scheme，以及任何 token、学生标识或敏感 query。日志/metrics/trace/audit/outbox/fixtures 通过 privacy canary，wire payload 通过 64 KiB 上限。本 Story 没有 UI；未来 UI 必须把 confirmed 表述为“外部系统已确认投递”，不能写成“业务部门已接收/已处理”。

### AC-1.9-SLO-BUDGET：五分钟确认预算可分解但不冒充生产 SLO

**Given** 健康的目标系统 non-production sandbox、PIC 内锁定的 integration measurement profile 和一条合成 `candidate.generated` 事实<br>
**When** synthetic producer 提交事务并由 reference relay 创建公共事项<br>
**Then** 从本地 commit time 到 provider 合同确认的总时长 `<= 5m`，evidence 分解 outbox wait、claim、network、provider acknowledgement 和 confirm CAS 时长；恰好 5 分钟通过，超过 5 分钟产生稳定 SLO failure/alert 且 DeliveryRecord 保持真实 pending/retrying/failed 状态<br>
**And** 同一 workItemKey 的 create/notification 重复率为 0；现有浏览器 `TEST-ENV-1.0.0` 不得用作网络/集成 profile。该结果只证明目标 non-production sandbox 与本次锁定 measurement profile 下的 synthetic contract budget，不得写成学校生产平台可用性、真实 Candidate 运行或 Story 5.5 业务 apply SLO。

### AC-1.9-AUDIT-OBSERVABILITY：授权、尝试、拒绝与对账可审计但不泄露

**Given** accepted/rejected/retry/confirmed/failed/reconcile/replay/gap/poison 任一路径<br>
**When** adapter 记录本地审计事实、结构化日志和指标<br>
**Then** 审计共同含 actor/workload pseudonym、action、aggregateType/tokenized aggregateId、channel、contractVersion、`provenanceMode`、generationKey token、source aggregateVersion、attempt/result/errorCode、traceId 和可信时间；stream 形状另必含 eventId、sourceFactId token、routeSequence、sourceFactDigest/eventPayloadDigest token 且禁止 intent fields，intent 形状另必含 deliveryIntentId token、requestDigest token 且禁止 event/fact/route fields。both/none/mode mismatch 拒绝；不得含 payload body、deliveryIntentId 原文、外部凭据、签名/nonce 原值、学生标识、自由文本、证据或第三方联系方式<br>
**And** reference adapter 使用 PIC lock 中的 integration audit vocabulary 构造 LocalAuditFact-shaped test records，并验证未来 owner 必须通过自身 local fact + audit outbox/ingress 归集、不得直接写 `audit_operations` schema。本 Story 没有生产 emitter，故不把 test action 注册为生产 audit 1.5，也不改写 1.0—1.4 digest；真实 producer Story 接入时必须发布相应 audit successor 后才能启用生产 action<br>
**And** 低基数 metrics 至少区分 channel/contractVersion/outcome、pending/retrying/failed 数量、attempt latency、gap/quarantine/reconcile count；不得把 aggregateId、eventId、externalId、nonce 或 error body 放入 metric label/trace baggage。

### AC-1.9-RELEASE-BOUNDARY：沙箱证据、发布绑定与后续 owner 诚实

## Dev Notes

### 必须先复用的现有能力

- `shared/outbox/LocalAuditFact` 与 `LocalAuditOutboxRecord` 是审计事实/审计 outbox；后者不是通用业务事件 envelope，公共 adapter 不得直接复用其业务语义。
- `AccessInvalidationConsumerWatermark` 已有 duplicate/stale/conflict/next/gap 判定；复用语义和测试思路，不把 identity-access 的业务类型搬入 shared。
- `AccessInvalidationOutboxRelayProcessor`、`AuditOutboxRelayProcessor`、`JdbcIdentityAuditRelayRepository`、`AuditRetryPolicy` 已展示 claim/publish/confirm、SKIP LOCKED、fencing、崩溃恢复和退避模式；只借鉴模式，禁止为本 Story 做跨域大重构。
- `SessionCommandService` 的 `scope + idempotency key + request digest + original result` 可作语义参考，但现有 session 保留窗口约 8 小时，不能满足 PIC 的 90 日合同。
- `contracts/events/envelope.schema.json` 是 permissive seed；`contracts/openapi/envelope.openapi.json` 已承载公共错误和 audit API。Story 1.9 使用独立 strict successor/合同包，通过一致性测试复用通用 envelope，不原位扩成集成大杂烩。
- `contracts/events/identity-access/consumer-registry-1.0.0.json` 已把 public-task 锁为 planned/not-installed。任何 checker/runner 不得修改其 lifecycle、required、activationAt、initialWatermark 或 runtime claim。

### 实现顺序与不可破坏的不变量

1. 先锁合同、registry、状态/错误/安全/retry/reconcile profile 和 fixtures，再写 Java/reference adapter；禁止从代码反推合同。
2. 固定 `domain <- application <- adapters`，跨模块只走公开 API/events；shared 继续只有 `id/time/error/trace/outbox`，不新增 `shared/integration`。
3. synthetic producer transaction 只用于证明协议，test SQL 不进入生产 migration；真实 producer 将来在自己 schema 原子保存业务事实+outbox+DeliveryRecord。
4. outbox delivery 为 at-least-once；aggregate-stream 依赖连续 routeSequence watermark + 严格递增但可稀疏的 source aggregateVersion，intent-command 依赖唯一 deliveryIntentId；二者共同使用 generationKey/providerEffectKey 和 fencing 提供可观察的“至多一次外部副作用”，不宣称基础设施 exactly-once。
5. `confirmed` 只表示外部系统按合同确认投递；business applied 必须由 owner 本地事务产生 apply record。二者状态、日志、指标、证据和 UI 文案永不共用。
6. 代表用户意图的高风险命令在本地事务提交前复用 Story 1.7 的 current authorization + final recheck；relay 只派发已提交 outbox，不在每次技术重试时重新解释用户权限。后续撤权/更正通过新的高版本事实关闭或修正外部事项。
7. 外部失败只推进 DeliveryRecord；本地业务状态不回退、不假成功。旧版、duplicate、gap、poison、timeout、部分成功和未知安全材料全部 fail closed 且可对账。
8. 任何秘密、敏感 payload 或外部 error body 不得进入 Git、审计、日志、metric label、trace baggage、DLQ evidence 或测试快照。

### 技术栈与版本约束

- 后端保持 JDK 25、Spring Boot 4.1.0、Spring Framework 7.x、PostgreSQL 18.4；沿用 Spring MVC/JDBC/显式 `TransactionTemplate`，不引入 WebFlux、Kafka、Redis、CloudEvents SDK、Flyway、ArchUnit 或 Spring Modulith。
- JSON 继续使用现有 Jackson；contract checker 使用当前受控 Python/toolchain。新增依赖只有在标准库/既有依赖无法满足已锁合同且 backend lock/SBOM/许可/漏洞门同步更新时才允许。
- outbound 使用可复用、不可变 JDK `HttpClient`，SSLContext、clock、timeouts、key/trust resolver 注入；请求级 timeout 与 connect timeout 分开，默认/显式禁止 redirect。
- SQL 继续参数化；多 worker claim 使用短事务、确定性顺序、`FOR UPDATE SKIP LOCKED` 和 fencing CAS。不要在网络调用期间持有数据库锁/事务。
- ID 为 UUIDv7；持久时间使用 `timestamptz`，wire 使用 ISO-8601 offset/UTC；错误 code 稳定、低基数，409 明确区分 idempotency mismatch/version conflict。

### Latest Technical Information

- OpenAPI 3.1.2 于 2025-09-19 发布；3.1 Schema Object 基于 JSON Schema 2020-12。合同使用精确 3.1.2/2020-12 语义，不降级到 3.0 nullable/discriminator 习惯。

- RFC 9421 要求应用 profile 明确签名覆盖组件；RFC 9530 的 `Content-Digest` 必须对实际传输 bytes 验证。只签 body digest 或自定义 body-only HMAC 不足以绑定 method/target/contract/timestamp/nonce。
- JWT workload identity 使用 RFC 7519 claims；`cnf.x5t#S256` 证书指纹绑定采用 RFC 8705 的 certificate-bound token 语义，防止脱离本次 mTLS 私钥持有者重放 token。
- Spring Boot 4.1.0 支持 Java 17—26；当前 JDK 25 合法。imperative JDBC 流程继续用 `TransactionTemplate`，网络 I/O 在事务外完成。
- JDK 25 `HttpClient` 设计为创建后复用并共享连接；SSLContext 和 redirect policy 在 builder 固定，请求 timeout 在 `HttpRequest` 固定。
- PostgreSQL 18 `SKIP LOCKED` 适合队列式 claim，但不是通用一致性视图；claim 查询使用稳定 order、短事务和 fencing 后置 CAS。
