## Story

作为数据责任人，
我希望按批次封账、用获批且可复现的质量口径计算不可变快照，并只发布通过质量门的完整事实，
以便我能判断数据是否可用于规则计算，定位失败批次、时间窗和影响范围，同时避免半批读取、历史改写或把技术故障伪装成业务质量失败。

## 业务与交付价值

- 建立 `ingestion-quality` 对 `DataBatch`、`NormalizedFact`、`QualitySnapshot` 的首个生产实现和唯一写边界。
- 将主键完整性、连续性、覆盖率、新鲜度四类质量指标变成带公式版本、原始分子/分母和阈值边界的可重放证据，而不是页面即时计算或自由文本解释。
- 只有 `sealed + quality-passed` 的完整批次可原子发布给下游；质量失败批次保留可下钻快照，但永不进入规则可见事实。
- 为 Story 2.4/2.5 的依赖资格与恢复，以及 Story 3.4/3.5 的 Candidate/Clue 证据绑定，提供自足、不可变、可验证的 snapshot handoff；本 Story 不提前实现这些下游领域。
- 让 R6 在 owned-source 范围内看到业务质量证据，让 R7 只看到技术作业/遥测；授权、审计、幂等、并发冲突和失败恢复均由服务端闭合。

## Story 元数据与实施边界

- **唯一硬依赖：** Story 2.1。Story 2.2 的重算模式可复用，但不是上游业务依赖；Story 2.4、2.5a-c、3.4、3.5 是本 Story 的消费者而非前置。
- **领域所有权：** `ingestion-quality` 唯一写 `DataBatch / NormalizedFact / QualitySnapshot`。模块内保持 `domain ← application ← adapters`；跨模块只通过公开 port/事实事件，不直接读写别域表。
- **冻结合同边界：** `contracts/data-catalog/qg-1.0.0.json`、`quality-gate.schema.json`、DCC-1.0.0、现有 field-projection binding 及各自历史 lock 的字节和摘要不可改写。现有 source override/SLO 自由文本不足以安全执行公式，开发者不得猜测或直接解析为运行逻辑。
- **ready-for-dev 解释：** 这里遵循 sprint-status 的文件工作流定义“Story 文件已创建”，不表示 Task 1-7 已获实施授权。G-03/G-07 已由 `AUTH-2026-07-17-001` 批准，不再等待新的常规外部 DoR；但当前 QG/DCC 已知不足以唯一编码全部可执行语义，因此开发者进入本 Story 后的第一个动作必须是 Task 0/correct-course，取得可引用的 derivation/decision profile 并锁定 executable metric policy 与 field-projection successor。该 profile 不存在时 Task 1-7 保持 blocked，不能用临时口头决定继续。
- **状态机边界：** 仅允许 `receiving → sealed → quality-passed → published` 或 `receiving → sealed → quality-failed`。无 reopen、无 failed→published、无 published→其他状态。迟到或纠正只能创建引用原批次的新 batch/lineage。
- **失败语义：** 只有一次输入完整、口径已批准且计算有效的评估低于门槛，才可写 `quality-failed`。口径缺失/摘要不匹配、时钟/KMS/DB/审计/outbox/worker 故障属于技术失败：批次保持 `sealed`，作业失败可见且可安全重试。
- **发布语义：** “发布”是 owner 本地事务中对 passed snapshot、批次状态及事实可见性的原子提交；外部 event relay 的 delivered 状态不得反向决定业务事务成功，也不得让消费者看到 half-batch。
- **下游 handoff：** 本 Story 交付稳定 `qualitySnapshotId`、不可变 contract/event/conformance fixture。实际 `RuleEvaluation/Candidate/Clue` 引用或复制快照由对应 Story 验收；在真实 consumer 安装前 `runtimeEvidenceClaim=none`。
- **权限边界：** RFP-1.0.0 已批准 R6 owned-source `QualitySnapshot` 读取和 `data-quality.read/repair/reconcile`，但未批准 `DataBatch` 对象，也未在现有 field-projection binding 中定义 QualitySnapshot DTO。Task 0 必须先发布字段分类/投影 successor；R6 表面仅列 assessed snapshot 及其冻结 batch metadata。receiving/sealed 无 snapshot 状态只属 R7 technical job，除非未来 RFP successor 明确增加 DataBatch。人工 seal/pass/publish 未获授权；不得私造 actionId。
- **估算校准：** 上游 `5d` 未覆盖首个批次/快照生产模型、可执行口径合同、PostgreSQL 状态/权限、durable worker、OpenAPI/事件、R6 页面、clean+upgrade 与 release evidence；建议 `8-12d`。容量仍限 5d 时先拆 Story，不得删减安全、证据或并发门。

### 本 Story 包含

1. 可执行质量口径 companion/successor、schema、fixture、digest lock 与 fail-closed loader。
2. `DataBatch` 收批、seal manifest/水位/截止时间、追加式 correction lineage，以及 `NormalizedFact` 的批次归属与发布可见性。
3. 四类质量指标的确定性计算、不可变 `QualitySnapshot`、阈值边界、适用性和原始计数证据。
4. passed-only 原子发布、failed 永不发布、幂等/CAS、事务审计/outbox，以及必要时带 lease/fencing/checkpoint 的持久评估作业。
5. R6 owned-source assessed-snapshot 列表、冻结 batch metadata、详情、趋势和异常范围下钻；R7 技术状态分面；OpenAPI/事件/授权 evidence。
6. PostgreSQL 18.4 clean+upgrade/actual-login、边界/并发/隐私/可访问性/性能及 release evidence。

- `RuleEvaluation`、个人基线、`CandidateAdmissionDecision`、`Candidate`、`Clue` 或关怀任务；不得创建 fake consumer 伪装 runtime closure。
- 人工修改质量结果、覆盖阈值、强制发布失败批次，或把 `data-quality.reconcile` 解释成授权改变 pass/fail。
- 在线扫描 raw/normalized 大表来渲染面板、将复杂桌面表格压进小屏 WebView，或缓存业务对象到 localStorage/IndexedDB/CacheStorage/Service Worker。
- 原位改历史迁移、DCC/QG/RFP/RS/PP/release 受控文件、`module-ownership.csv`，或新增依赖/升级 PAB 锁定工具链。
- 完整告警/运维中心、质量熔断和恢复闭环；本 Story 只输出下游可消费的质量事实。

## Acceptance Criteria

### AC-2.3-HAPPY：封账、判定与发布（受控原始 AC）

**Given** 批次状态机、质量公式和截止时间已版本化并获批<br>
**When** 数据责任人执行本 Story 的主流程<br>
**Then** 仅允许 `receiving→sealed→quality-passed→published` 或 `receiving→sealed→quality-failed`；failed 永不 published；质量快照可下钻并提供稳定 handoff 供下游随 Candidate 保存<br>
**And** 服务端授权、失败可见、审计、幂等和 `aggregateVersion` 冲突路径必须通过自动化或可复现验收。

### AC-2.3-EXECUTABLE-CONTRACT：质量口径可执行、可复现且失败关闭

**Given** 当前 QG/DCC 的数值门和 source-specific 自由文本，以及 FR-11/NFR-9 对公式证据的要求<br>
**When** Task 0 完成 readiness closure<br>
**Then** 新增独立受控 companion/successor，逐指标锁定 `metricId/formulaId/formulaVersion/unit/operator/inclusive|exclusive boundary/threshold/numerator/denominator/denominatorZeroBehavior/valueScale/roundingMode/comparisonStage/window/cutoff/timezone/applicability/sourceId/owner/approval/effectiveAt/evidenceRef/canonicalizationProfile`，并以 JSON Schema 2020-12、有效/无效/boundary fixture 和摘要 lock 验证<br>
**And** 至少覆盖主键完整性、连续性、覆盖率、新鲜度及 QG 的 required-field/valid-record/P0 mapping/core-field/arrival/conflict/duplicate/version-regression 门；source override 必须成为结构化值，不从自由文本临场推导<br>
**And** 比率采用获批的精确 rational/BigDecimal 或整数 basis-point 算法，明确 scale/rounding mode、先比较还是先舍入及 canonical JSON；禁止 binary floating point 决定 pass/fail/hash，并以 Java/SQL 跨实现 fixture 证明一致<br>
**And** 公式、分母、单位、阈值等于时的包含性、零分母、截止时间、时区或 source applicability 任一无法从已批准输入唯一确定时 fail closed 并停止 Task 1-7；这表示 planning baseline 缺陷，必须 correct-course，不得选择“看起来合理”的默认值或临时批准<br>
**And** 历史 DCC/QG/lock 字节与摘要保持不变；运行时同时校验 policy version+digest，未知版本或 digest mismatch 不得 seal/evaluate/publish。

### AC-2.3-BATCH-LIFECYCLE：批次状态与 lineage 在应用层和数据库双重锁死

**Given** 某 source 的 business batch key/version、接收记录、schema/catalog/policy 版本、水位和受信截止时间<br>
**When** 创建、重放、封账、迟到或更正批次<br>
**Then** 新批次唯一合法初态为 `receiving`；相同 `sourceId+businessKey+sourceVersion+manifestDigest` 重放幂等，相同业务身份不同内容冲突失败；seal 冻结 manifest、record counts、observation window、cutoff、timezone、watermark、schema/catalog/quality policy versions+digests<br>
**And** domain 与 PostgreSQL function/constraint/CAS 只允许两条规定路径；raw DML、re-seal、reopen、publish-before-pass、failed→published、published→回退和旧 aggregateVersion 全部失败且不留部分写入<br>
**And** 迟到/纠正创建新 `batchId`，保存 `supersedesBatchId/lineageId/reason/effectiveAt`；旧 batch、snapshot 和事实不修改，原 source business key/version 语义不丢失<br>
**And** `NormalizedFact` 必须绑定 batch/record identity、source/schema version 与 lineage；sealed 前及 failed batch 的事实永不进入规则可见投影。

### AC-2.3-QUALITY-CALCULATION：四类指标边界确定且保留原始证据

**Given** 一个已封账且 manifest/policy digest 未变化的批次<br>
**When** 使用该批次冻结的 metric policy 计算质量<br>
**Then** 每个适用指标保存 `numerator/denominator/value/unit/operator/threshold/boundary/result/reason`；`rawCount` 不作为独立字段，ratio/count/duration/composite-and 的原始整数证据由 `DEC-019 §4.9 / QSHM-1.0.0` 的闭合 numerator/denominator 映射及 sealed manifest 表达；结果可由同一冻结业务输入按 QSHM exact material、QMDP 顺序、显式 null 与 canonical time 重放到同一 immutable hash<br>
**And** P0 主体标识完整率目标至少 99.5%、核心场景字段覆盖率至少 98%、新鲜度至少 99%，但具体 source 门、连续性/覆盖率口径和 hard-failure 语义只能来自获批 companion；不得把 PRD 目标自行扩成未批准公式<br>
**And** 自动测试覆盖 threshold 精确相等、±1 最小计量单位或 basis point、零分母、无适用记录、半开窗口、UTC/`Asia/Shanghai`、DST 输入、截止时刻、source override、重复业务键、版本倒退和 manifest/policy digest race<br>
**And** 仅完整且有效的评估可得 overall pass/fail；technical/contract error 不产生 fail snapshot，不污染质量趋势。

### AC-2.3-SNAPSHOT-PUBLICATION：快照不可变且通过后原子发布

**Given** 当前 aggregateVersion 的 sealed batch 和一次完整质量评估<br>
**When** 提交评估或发布<br>
**Then** `QualitySnapshot` 保存 batch/source、gate/metric-definition version+digest、窗口/cutoff/watermark/manifest、evaluatedAt、overall result、每项指标证据、owner/approval evidence、lineage、traceId 和 immutable hash；业务角色、在线角色、quality worker 和 raw DML 均禁止 update/delete<br>
**And** snapshot + `sealed→quality-passed|quality-failed` + local audit + outbox + idempotency result 在一个 owner 本地事务全成或全败；publish 再以 CAS 原子完成 `quality-passed→published` 和该 batch 全部事实可见性，不存在 half-batch read<br>
**And** quality-failed 只发自足 assessed fact，不发布 normalized facts；published event 只可能来自 current passed version，且事件包含消费者做决定所需的 manifest/watermark/policy/snapshot 事实而非仅一个 ID<br>
**And** audit/outbox/DB 故障回滚业务提交；relay 重试不反向改写已提交业务结果。

### AC-2.3-AUTH-AUDIT-IDEMPOTENCY：授权、失败、审计与冲突均服务端闭合

**Given** 当前 RFP、owned-source evidence、identity generation、policy/objectVersion、受信时间与审计依赖<br>
**When** R6/R7/越权用户读取或受信 workload 提交 seal/evaluate/publish 命令<br>
**Then** R6 仅能读取 owned-source QualitySnapshot 最小投影及其中冻结的 assessed-batch metadata；`DataBatch` 不是当前 RFP 对象，receiving/sealed 业务列表默认拒绝。R7 仅能读取技术 Job/Telemetry/traceId；对象不存在与越权响应不可区分，hidden 字段不进入 JSON/DOM/cache/a11y tree<br>
**And** 每次请求及序列化前重检 human authorization；snapshot→persisted source→owner 使用 DB-backed derived evidence，不把 snapshotId 伪装成 source digest，也不向冻结 owner-bindings mount 写动态行。owner 变化立即改变 R6 可见性，但不得改写历史 snapshot 或令输入/策略未变的自动评估失败<br>
**And** workload command authorization 与 R6 human read authorization 分离：锁定 workload principal/mTLS identity、command audience/capability、role-to-login 映射、撤权和 replay 语义；worker final commit 重检 workload capability、policy approval evidence 和数据版本，而不是当前 R6 UI scope<br>
**And** 每个命令携带 `Idempotency-Key + expectedAggregateVersion`；幂等 scope 为 `tenant+actor/workload+commandType` 并保留 90 日，同键同 body 返回原结果，同键异 body 或 stale version 返回 409，envelope 含 `code/message/traceId/fieldErrors/currentVersion/latestActor/latestActionAt`<br>
**And** 状态变更与 `LocalAuditFact` 同事务；审计不可用阻断命令。敏感快照下钻如按策略需要 read audit，必须先成功提交读审计再返回内容。

### AC-2.3-CONCURRENCY-DEPENDENCY：并发 worker 不得提交混合或陈旧结果

**Given** 质量评估或事实发布需要异步扫描/汇总，或一个 worker 在运行期间发生超时、接管、取消、policy 变更或授权依赖降级<br>
**When** 作业 claim、checkpoint 或最终提交<br>
**Then** 作业状态持久化为 `queued→running→succeeded|failed|cancelled`，attemptNo 单调，lease/fencingToken/checkpoint 均由 DB CAS 保护；过期 token 在 checkpoint 和 final commit 都不能写 snapshot、batch、audit 或 outbox<br>
**And** final commit 重检 batch 仍 sealed、aggregateVersion、manifest/watermark/policy digest、workload capability、冻结的 policy approval evidence 与依赖健康；任何变化保持 sealed 并给出可重试技术失败，不提交混合版本 pass/fail<br>
**And** crash/takeover/lease expiry/stale worker/duplicate dispatch/gap/poison 路径可恢复且只产生一个有效结果；consumer 对 duplicate/old 幂等，对 gap 暂停并 backfill/replay，对 poison 隔离，不静默跳过。

### AC-2.3-DRILLDOWN-TREND：R6 可定位质量结论而不在线扫描事实

**Given** R6 进入 desktop `data-quality-panel` 的“批次与质量快照”子表面且拥有一个或多个 source<br>
**When** 查询 assessed snapshot 列表、冻结 batch metadata、详情、趋势或异常范围<br>
**Then** 页面显示 source、评估后批次状态、数据截止/更新时间、policy version、四类指标、pass/fail、时间窗、影响范围和可验证的 numerator/denominator；图表与无障碍表格使用同一只读 QualitySnapshot DTO<br>
**And** 列表分页/排序/筛选由 URL 恢复，详情读取物化 snapshot/聚合计数而非在线扫描 raw/normalized facts；无数据不显示虚构 0，trend 不混合不同 formulaVersion 也不把 technical failure 算作 quality fail<br>
**And** loading/empty/filter-empty/error/forbidden/degraded 使用 `state-panel` 且只有一个真实 next step；error 保留筛选，重试幂等，状态不只靠颜色表达，键盘/读屏/200% zoom/1366/1440 自动验证<br>
**And** 依赖树、required/optional/combinator、QRP、fused/recovering/eligible 区域标记为 `pending-story-execution/not-available`，不返回空数组、假 eligible 或恢复动作，并为 2.4/2.5 保留稳定 composition boundary<br>
**And** `<768px` 不承载复杂质量表格；离线只显示无业务对象的网络状态，不缓存卡片或命令。R6 business quality 与 R7 technical operations 使用不同 DTO/route，不靠前端隐藏字段分面。

### AC-2.3-DOWNSTREAM-SNAPSHOT：为 Candidate/Clue 提供自足 handoff 而不越权实现

**Given** passed 或 failed 的不可变 QualitySnapshot<br>
**When** 发布 `scholarsense.ingestion-quality.data-batch.quality-assessed.v1`，或 passed 后发布 `scholarsense.ingestion-quality.data-batch.published.v1`<br>
**Then** CloudEvents/PIC envelope、JSON Schema、≤64 KiB、UUIDv7、source+id 唯一、aggregateVersion 单调且 payload 自足；提供 valid/invalid/duplicate/old/gap/poison conformance fixture<br>
**And** handoff 足以让后续 Candidate/Clue 保存 `qualitySnapshotId` 和产生时证据，不要求其回读可变“latest”；本 Story 不创建下游表/代码，consumer 未安装时明确 `runtimeEvidenceClaim=none`<br>
**And** quality-failed 事件不直接写 `QualityEligibility` 或熔断/恢复状态；这些决定严格留给 Story 2.4/2.5。

### AC-2.3-EVIDENCE：证据、保留、性能与隐私声明真实

**Given** G-03、RS-1.0.0、PP-1.0.0 和生产证据门<br>

### 开发者首读：不可突破的五条不变量

1. **先合同、后计算：** 当前 QG/DCC 不是足以执行 FR-11 的公式语言，现有 field-projection 也没有 QualitySnapshot schema。Task 0 将既有批准语义物化并锁定；checker 通过前不写计算器、DDL 或 UI。
2. **旧批次永不改：** seal 后 manifest/版本/水位冻结；迟到/纠正只建 successor。质量失败与技术失败必须是两种状态/证据。
3. **只发布完整 passed batch：** snapshot、状态、audit/outbox/idempotency 原子；publish 与整批 fact visibility 原子；failed 永不发布。snapshot 业务不可变，但不绕过受控 retention。
4. **领域边界不前移：** 2.3 只交付 snapshot handoff；不实现 2.4 eligibility、2.5 fuse/recovery 或 3.x Candidate/Clue。
5. **证据不虚报：** 未激活 consumer/生产时长/学校部署输入保持 none/deferred；不要用 fixture 或测试计数替代目标运行证据。

### 当前仓库现实与复用点

- 当前生产代码已有 data catalog、publication CAS、subject-window recompute、lease/fencing/checkpoint、audit/outbox/idempotency、owner evidence、startup privilege gate；尚无 `DataBatch/NormalizedFact/QualitySnapshot` 实现。扩展现有 hexagonal conventions，不另建第二套框架。
- `backend/src/main/java/cn/edu/suda/scholarsense/ingestionquality` 是 owner 模块；`module-ownership.csv` 已正确登记三个对象，保持不变。
- `FrozenDataCatalogPolicy` 与 catalog lock 保护历史 DCC/QG；新 executable policy 使用独立 loader/port 和独立 lock，避免让旧 loader 承担未定义语义。
- `MappingRecomputeJob`、`SubjectWindowRecomputeProcessor`、`JdbcSubjectWindowRecomputeStore` 提供 job/fencing 模式；复用概念和基础设施约定，不复用其 subject-recompute 业务表或 identity。
- `CatalogOwnerEvidenceProvider` 只覆盖 SOURCE/DEPENDENCY/SUBJECT_MAPPING_EXCEPTION/JOB；为 QualitySnapshot 新增 DB-backed derived path，并测试 snapshot→source 在授权决定与序列化之间变化的 race。
- RFP 已含 `ObjectClass.QUALITY_SNAPSHOT`，但 `ProjectionObjectClass`、`FieldProjectionCatalog` 和 `contracts/field-projection/field-projection-policy-binding-1.0.0.json` 均无 QualitySnapshot schema；必须出 successor，不能仅在 controller 手写 DTO allowlist。RFP 未含 DataBatch。

### 领域与事务设计约束

- 推荐 batch 字段：`batchId(UUIDv7), sourceId, businessKey, sourceVersion, status, aggregateVersion, manifestDigest, record/valid/rejected counts, observation [start,end), cutoffAt, timezone, watermark, schema/catalog/policy versions+digests, received/sealed/evaluated/publishedAt, supersedesBatchId, lineageId, traceId`。
- snapshot 至少保存 AC-2.3-SNAPSHOT-PUBLICATION 所列上下文和逐 metric 原始证据；只保存聚合计数，不把学生/原始记录复制进 snapshot、event 或 telemetry。
- 使用显式 aggregateVersion/CAS 和 DB row/advisory locking 中已验证的最小机制；不要依赖进程内 mutex。PostgreSQL CHECK 不能引用其他表，跨表 transition/immutability 用受控 function/trigger/transaction invariant。
- workload 命令与 R6 查询分离。worker 使用冻结的 principal/capability/audience/DB login 合同；R6 owner scope 只控制 human visibility。R6 只能对 owned `Source` 提交 source-scoped reconcile intent，Job claim/retry 属 workload 或 R7 `platform.retry`；任何人都不能借 reconcile 改结果、阈值或强制发布。所有 authorization 在 server，DTO 按业务/技术分面独立定义。
- 事件遵循 owner-single-writer、transactional outbox、at-least-once delivery；`type` 必须是 `scholarsense.<domain>.<aggregate>.<event>.v1`。消费者用 persisted inbox/watermark，gap 不可静默越过。`source+id` 唯一，wire time 为 ISO-8601 offset，DB time 为 UTC。
