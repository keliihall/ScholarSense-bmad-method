## Story

作为授权管理员，
我希望权威辅导员—责任学生关系与学院归属持续同步、每日对账，并让无有效接收人的异常可见，
以便平台只把学生对象交给当前有效责任人，且任何缺失、冲突或陈旧关系都失败关闭、可追踪并可恢复。

## 业务与交付价值

- 在 Story 1.6a 的权威账号、R1—R7 角色、组织/任职与独立 checkpoint 底座上，形成“受控学生来源引用 → 当前责任辅导员 → 学院组织”的服务端责任 scope anchor。
- 将来源版本、水位、有效区间、当前接收人有效性、每日全量差异和学院异常队列持久化，使授权和后续责任转移不依赖前端声明、人工改库或隐式兜底。
- 为 1.6c 的更正/撤权传播、1.7 的 object/action/scope 授权和 3.9b 的未完成事项转移提供稳定、版本化、可对账输入。
- 保持学校权威源的所有权：平台只保存当前授权与历史追责所需的最小版本化事实，不建设第二套责任关系主数据。

### 本 Story 包含

1. 冻结责任增量、完整全量 snapshot、当前责任 scope、接收人有效性、对账结果与学院异常队列的 provider-neutral 合同、正反 fixtures、checker 和独立 contract lock。
2. 消费 `consumerProjection=responsibility`，追加不可变责任 source fact，并维护可重建的当前责任关系投影。
3. 以 1.6a 当前账号、`R1-COUNSELOR` 任职和 active 学院组织校验接收人；依赖落后、歧义、冲突、过期或无效时 fail closed。

5. 建立无有效接收人的学院异常队列；只由更高权威版本自动收敛，不提供手工改关系或隐式分派后门。
6. 在 `identityaccess.api` 提供 transport-neutral 的当前责任 scope 查询端口，供后续 1.7/3.9b 使用。
7. 复用 identity-access 的 LocalAuditFact/outbox、trusted time、UUIDv7、traceId、持久 lease/fencing、保留绑定和 PostgreSQL 真实集成测试。
8. 产出同一 trace 贯通受控 source、responsibility worker、PostgreSQL、责任 scope read-back、全量对账和异常队列的非生产沙箱证据。

## Acceptance Criteria

### AC-1.6b-HAPPY：责任增量原子形成当前 scope anchor

**Given** 1.6a 的 `identity-org` checkpoint 已达到责任批次声明的 supporting watermark，且 `SRC-P0-RESPONSIBILITY-001` 发布签名、连续、合同有效的 responsibility 增量<br>
**When** responsibility worker 在有效 lease/fencingToken 下处理批次<br>
**Then** 平台在一个本地事务中追加不可变责任事实，更新当前责任投影、责任 checkpoint、job/attempt、接收人有效性、必要异常队列、LocalAuditFact 与 audit outbox，并保存 source/schema/contract version、source watermark、effective interval、aggregateVersion、traceId 与可信时间<br>
**And** 提交后经公共责任 scope 查询端口 read-back 的可见时间才记为 `authorizationEffectiveAt`；fixture 必须证明 `authorizationEffectiveAt - sourceVisibleAt ≤ 15m`，job 开始、HTTP 接收或 DB insert 时间不得冒充授权生效。

### AC-1.6b-CONTRACT-REFERENCE：合同、引用与 supporting watermark 失败关闭

**Given** 批次出现错误 source/projection/schema/contract/digest/signature、未知字段破坏性变更、重复关系键、非法有效区间、空值/格式错误/合同不合法的学生来源引用、未知/停用账号、未知/停用学院，或责任批次依赖的 identity-org watermark 尚未到达<br>
**When** worker 校验并规范化批次<br>
**Then** 坏记录/批次不更新当前投影、不推进 responsibility checkpoint，也不推进或回退 identity-org checkpoint；按稳定 reasonCode 持久化最小隔离诊断、payload digest、job/attempt 与拒绝审计<br>
**And** 仅“已在同一一致性基线确认的无有效接收人”形成学院异常；单纯 identity-org 落后属于 dependency unavailable/retry，不能制造假异常或猜测接收人；在 `subject-registry` 尚无批准查询端口时，不得声称已校验 canonical StudentRef 是否存在。

### AC-1.6b-RECIPIENT-VALIDITY：有效接收人与无接收人唯一判定

**Given** 使用受信 `serverNow` 计算某学生当前责任关系<br>
**When** 查询当前责任 scope<br>
**Then** 只有关系为 active、时间位于 `[effectiveFrom,effectiveTo)`、恰有一个合同允许的当前主责任人、责任账号 active、存在有效 `R1-COUNSELOR` 任职、学院组织 active，且关系学院与任职 scope 按责任合同一致时返回有效接收人<br>
**And** zero/multiple recipient、重复或重叠关系、inactive/non-R1 counselor、学院缺失/停用/不匹配、恰在 `effectiveTo`、版本冲突、IAM/可信时钟不可用均返回 `INVALID|DEPENDENCY_UNAVAILABLE` 的稳定无泄露 scope-validity 结果；该 DTO 不得依赖 RFP、返回 `ALLOW` 或冒充 1.7 的完整授权结论，也不得回退给旧责任人、学院默认人、最近更新者或 DelegationGrant。

### AC-1.6b-DAILY-RECONCILIATION：每日全量同水位对账

**Given** 受控 profile 在 `Asia/Shanghai` 每日 06:00 正常触发，或 worker 重启后发现批准 catch-up 窗口内尚无终态 run 的 `businessDate`，且 source 提供签名、sealed、scope 完整的全量 snapshot manifest/partitions<br>
**When** scheduler 只负责 enqueue 持久 job，worker 获取 lease 后执行对账<br>
**Then** 以 `(sourceId,feedId,partition/scope,consumerProjection,businessDate,jobKind)` 唯一键至多 enqueue/完成一次每日 run；停机不得静默跳过，超出 catch-up 窗口或 source 已无法提供该日 sealed snapshot 时保存显式 missed/failed 证据并告警<br>
**And** 只有所有声明 partitions 齐全、count/digest/completeness 通过，且 expected source snapshot 与本地不可变事实在相同 sourceVersion/throughWatermark 上形成一致快照时，才保存一次完整 reconciliation run<br>
**And** 结果至少保存 runId、source/projection/schema/contract version、source/identity-org watermark、expected/actual count/digest、matched/missing/unexpected/versionDrift、matchRate、activeUnmappedCount、exceptionCount、started/completedAt、outcome/reasonCode 与 traceId；按已批准口径 `matchRate ≥ 99.9%` 且 `activeUnmappedCount=0` 才标记质量通过。

### AC-1.6b-RECONCILIATION-TRUTH：作业完成不冒充对账达标

**Given** 全量比较完成但存在 missing、unexpected、version drift、重复键、无有效接收人或低于 99.9% 的结果<br>
**When** worker 提交 reconciliation run<br>
**Then** job 的 `succeeded` 只表示比较与证据持久化成功，必须同时保存独立 `reconciliationOutcome=differences-found|threshold-failed` 并在技术/学院适用表面明确失败，不得显示“对账通过”<br>
**And** 对账不得直接覆盖历史或绕过正常 ingest 改库；missing 通过既有 replay/backfill 入口收敛，unexpected/version drift 令受影响 scope fail closed 并进入异常，直到更高权威版本和后续对账解除。

### AC-1.6b-EXCEPTION-QUEUE：学院异常队列可追踪且不可手工伪修复

**Given** 在一致的账号/组织/责任水位上确认某当前关系无有效接收人或对账差异使接收人不可信<br>
**When** responsibility transaction 提交或每日对账落盘<br>
**Then** 按稳定业务键幂等创建/更新学院异常，保存学院受控引用、学生来源 token/digest、reasonCode、sourceVersion/watermark、firstSeenAt/lastSeenAt、status、aggregateVersion 与 traceId，不保存学生姓名、学号、账号明文或自由文本<br>
**And** 由增量接收人校验打开的异常，在更高、连续的权威增量恢复唯一有效接收人并由 scope read-back 确认后立即以追加历史 + 当前 resolved 投影收敛，不得等待次日对账而违反 15 分钟目标；由每日差异打开的异常或 quality gate 只有在后续同水位对账 matched 后解除<br>
**And** 不允许 UI、SQL、运维重试或重复事件直接指定接收人、删除历史或关闭未解决异常。

### AC-1.6b-AUTHORIZATION-BOUNDARY：不发明角色、动作或完整授权器

**Given** RFP-1.0.0 没有名为“授权管理员”的技术角色，也没有单独 `responsibility.reconcile` action<br>
**When** 自动作业、技术观察或学院异常消费发生<br>
**Then** worker 以受控 service identity 自动执行；本 Story 只发布供 1.7 消费的最小读模型/端口，不开放 R2/R6/R7 人工 HTTP/UI。候选授权必须引用展开后的单一 actionId：R6 为 `data-quality.read`、`data-quality.reconcile`，R7 为 `platform.read`、`platform.diagnose`、`platform.retry`、`platform.reconcile`；任何字面含 `/` 的 actionId 一律 deny<br>
**And** R6 的 ownerBinding 权威来源、存储、查询与正反 oracle 尚未落地，归 1.7 的完整 object/action/scope 决策；在其批准前不得宣称 R6 owned-source read 已授权。R2 学院异常最小投影也仅作为 1.7 消费合同。不得发明角色/action，也不得把组织 membership、前端 role、OIDC 展示 claims 或缓存单独当作学生访问授权。

### AC-1.6b-IDEMPOTENCY-ORDERING：重放、旧版、乱序与 gap

**Given** 相同 event/batch/snapshot 重放、同稳定关系键异 payload、旧 sourceVersion、乱序记录或 watermark gap<br>
**When** responsibility pipeline 处理输入<br>
**Then** 相同键同 payload 返回原结果且不重复关系、异常、审计或对账 run；同键异 payload 返回稳定冲突，旧版不能覆盖新版，gap 只暂停对应 responsibility checkpoint 并请求连续补拉<br>
**And** replay/snapshot 必须证明请求范围、完整 scope、签名/digest 与单调版本；identity-org 成功水位不得遮蔽 responsibility 落后，responsibility 成功也不得推进 identity-org。

### AC-1.6b-CONCURRENCY-ATOMICITY：双 worker、fencing 与聚合版本

**Given** 两个 worker/scheduler 同时竞争相同 source/feed/partition/projection，或租约在长事务期间过期、关系版本在提交前变化<br>
**When** 旧 fencingToken 或旧 aggregateVersion 尝试提交<br>
**Then** 数据库以提交时有效 lease/fencing 与条件版本更新拒绝旧 worker；旧 worker对事实、投影、异常、checkpoint、job 结果、审计和 outbox 均为零提交<br>
**And** 核心 ingest 事务中的事实、当前投影、异常队列、checkpoint、job result、LocalAuditFact/outbox 任一点故障注入都使合法批次事务回滚；提交后的 scope read-back/SLO evidence 失败不得倒退已提交事实或 checkpoint，而须进入失败分母并持久化可重试 compensation。隔离诊断使用独立最小事务且同样受当前 fencing 保护。

### AC-1.6b-DEPENDENCY-FAILURE：依赖故障与可恢复状态

**Given** source/network、workload identity、签名、KMS/config、数据库、审计、IAM/identity current projection、可信时钟、identity-org supporting checkpoint 或 snapshot partition 任一不可用<br>
**When** 增量或全量作业无法安全完成<br>
**Then** 作业进入真实 retrying/failed 路径并保存稳定原因，responsibility checkpoint 与“上次每日对账成功”不前移；未知/受影响 scope fail closed，不把旧关系伪装为已确认实时结果<br>
**And** 恢复后从最后已提交水位幂等追平；只有连续补拉/完整 snapshot、当前接收人 read-back 与新对账证据通过后才恢复 fresh/valid。

### AC-1.6b-SLO-OBSERVABILITY-PRIVACY：可观测、可审计、最小化

**Given** 增量、heartbeat、对账、差异、隔离、异常打开/解除和失败路径<br>
**When** 记录运行与审计证据<br>
**Then** traceId 贯通 source、job/attempt、lease、DB、scope read-back、reconciliation、exception 和 audit relay；指标至少覆盖 last success、watermark lag、15m 达标率、daily run age/outcome、matchRate、active-unmapped、open exceptions、retry/quarantine<br>
**And** metric labels、日志、trace、错误、异常技术摘要和 audit payload 不含学生/账号/外部 ID 明文、原始 payload、token 或密钥；高基数对象只使用不可逆 token/digest，审计失败不得让关键变更成功。

### AC-1.6b-DOWNSTREAM-BOUNDARY：为后续 Story 提供输入但不越界

**Given** 责任关系创建、变化、失效或每日对账发现差异<br>
**When** 本 Story 发布/暴露结果<br>
**Then** `identityaccess.api` 只提供当前责任 scope、来源版本/水位、aggregateVersion、有效区间、freshness/validity 与受控接收人引用，供 1.6c/1.7/3.9b 消费<br>
**And** 本 Story 不发布跨模块 lineage/supersedes 撤权事实，不更新 Candidate/Clue/workItem，不重置 dueAt，不通知旧/新责任人，不创建 DelegationGrant，也不声称 FR-2/NFR-27 已 full。

### AC-1.6b-VERIFICATION：真实证据与完整回归

**Given** 合同、实现与受控 responsibility 沙箱可执行<br>

## Dev Notes

### 不可协商的领域与安全决策

1. **学校是关系权威，平台是版本化消费者。** 不提供责任人手工编辑、默认学院人员、模糊匹配或直接 SQL 修复。
2. **责任关系不是 DelegationGrant。** 永久权威关系和有期限代办必须分离；1.6b 不创建/消费 grant 作为权威接收人。
3. **组织不是学生授权。** 组织/任职只参与接收人有效性；学院 membership 本身不能让用户查看全院学生。
4. **StudentRef 所有权不转移。** identity-access 只保存受控 source ref token/digest；canonical `StudentRef/SubjectMapping` 由 subject-registry 独占。
5. **支持事实必须同水位。** responsibility 不得在 identity-org supporting watermark 落后时确认接收人或推进自己的 checkpoint。
6. **增量不是全量。** 增量批次只验证出现的记录及其已有引用，不要求每批同时包含账号/组织/全部关系，也不得删除未出现关系。
7. **完整全量必须证明 scope。** partial/unsealed/missing-partition snapshot 不能推进“每日完成”状态，也不能用缺失记录批量失效当前关系。
8. **对账证据不直接改库。** 差异通过 replay/正常 ingest 收敛；对账只形成证据、fail-closed gate 和异常。
9. **作业成功不等于质量通过。** job 状态与 reconciliation outcome 正交，UI/指标不得把 completed comparison 冒充 threshold pass。
10. **历史追加、当前可重建。** 关系事实和异常历史不可覆盖；当前投影可重建并带 source/aggregate version。
11. **fixture 不是生产。** 受控本地沙箱必须标记 `productionEligible=false`，静态 Gate 不替代真实运行证据。
12. **保留是运行绑定。** 新对象必须引用 RS-1.0.0、owner/effectiveAt/legal hold/consumer watermark；只写文档期限不算完成。
13. **增量与全量作业不可混型。** 现有 sync job 没有 jobType；必须用独立 reconciliation job，或受控引入 `jobKind` 并同步修正 claim/唯一键/路由，不能让同一 projection 的两种作业互领。
14. **异常解除遵守来源语义。** 增量有效性异常恢复后立即 read-back 并收敛；只有由全量差异产生的异常/quality gate 才等待后续 matched reconciliation。
15. **post-commit SLO 不伪装成原子事务。** 核心事实先原子提交；随后 read-back/evidence 失败进入分母和持久补偿，不能回滚已提交事实，也不能假装证据成功。

### 建议规范化合同

provider-specific payload 只存在于 outbound adapter；application 使用的 responsibility normalized record 至少表达：

- envelope：`sourceId`、`feedId`、`partitionId`、`consumerProjection=responsibility`、schema/contract version、batch/event/snapshot ID、sourceVersion、from/to/through watermark、按分区键控的 supporting identity-org watermark vector（合同证明单分区时可 scalar）、sourceVisibleAt、observedAt、trace/correlation。
- relation：稳定 relation externalRef token/digest、带 purposeCode/keyVersion 的 student source ref token/digest、counselor account ref token/digest、college organization ref token/digest、contract-defined responsibility type、status、effective interval、recordVersion、payloadDigest。
- full snapshot：snapshotId、scope/partition manifest、partNo/partCount、sealed/complete、cutoffAt、throughWatermark、expectedCount、canonicalDigest、contractVersion。
- current scope：受控 student token、counselor accountId、college organizationId、sourceVersion/watermark、aggregateVersion、effective interval、`VALID|INVALID|DEPENDENCY_UNAVAILABLE` scope validity/freshness、reasonCode；不得包含 `ALLOW`。
- exception：exceptionId/businessKey、college/student tokens、reasonCode、first/last seen、open/resolved、sourceVersion/watermark、aggregateVersion、traceId。
- reconciliation：runId、source/projection/contract version、watermarks、expected/actual digest/count、分类计数、批准公式得出的 matchRate、activeUnmappedCount、outcome/reason、times、traceId。

wire cursor 和供应商字段由责任合同冻结；domain/api 不得出现供应商 SDK/cursor 类型、学生/账号明文或可变显示名。

### 每日对账与 15 分钟口径

- `@Scheduled`/cron 只是触发器；06:00 的正确性状态必须是 PostgreSQL 中可恢复、可 fencing 的 job/run。
- “每日完成”要求在一个受控日历日内产生完整、同水位、证据已持久化的 run；缺 partition、依赖失败或证据事务失败不算完成。
- 06:00 停机不等于跳过该日：在批准 catch-up 窗口内按 businessDate 幂等补排；无法取得对应 sealed snapshot 时记录 missed/failed 与告警，不能拿次日快照冒充前一日完成。
- 生产 `matchRate` 必须使用 Task 1 批准的公式；Story 只固定阈值 ≥99.9% 和 active unmapped=0，不允许代码另造分母。
- 增量 SLO 从权威源版本可见的 `sourceVisibleAt` 到公共责任 scope 查询真正返回该 sourceVersion/watermark 的 `authorizationEffectiveAt`。
- 恰好 15 分钟通过，超过 15 分钟失败；read-back 空、IAM/identity projection/clock unavailable 和 SLO evidence 写失败必须入分母/补偿，不能消失。

### 架构一致性

- 继续模块化单体和 `domain ← application ← adapters`；跨模块只经 `identityaccess.api` 或后续版本化事件。
- `identity-access` 拥有责任授权事实/投影；`subject-registry` 拥有 StudentRef，`clue-care` 拥有 Candidate/Clue/workItem，禁止跨模块表/FK。
- 控制器、scheduler、source adapter 不直接写业务表；只调用 application use case/command。
- 正确性状态在 PostgreSQL；内存缓存、单机锁、cron 是否触发不能决定水位、接收人、异常或对账成功。
- 本 Story 不实现人工 HTTP/UI；只发布 transport-neutral 内部端口与最小 projection，实际 R2/R6/R7 object/action/scope 授权和 ownerBinding 归 1.7。
- UUIDv7；UTC 存储；API ISO 8601 offset；所有 business/read model response 携带 aggregateVersion 和 source watermark。
