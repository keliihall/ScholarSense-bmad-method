## Story

作为数据责任人，
我希望向规则域表达 `eligible`、`fused` 与 `recovering`，
以便规则域只基于已验证、版本连续且全部 required 依赖合格的质量事实决定是否可计算，坏数据不会制造新的 `RuleEvaluation`、`Candidate` 或 `Clue`，且失败成员、水位和恢复状态可追溯。

## 业务与交付价值

- 把 Story 2.1 的稳定 `sourceId → dependencyId` 和 RC-1.0.0 的 RuleVersion 组合声明变成可执行、可锁定的 `RuleDependencyRegistry`，消除规则域自行拼接依赖的风险。
- 把 Story 2.3 的不可变质量快照转译为 owner-local `QualityEligibility` 事实；未知合同、摘要漂移、乱序或间隙均失败关闭，不把技术错误伪装成质量失败。
- 为 Story 2.5 的熔断/恢复、Story 3.2 的生产规则质量门和后续场景发布提供稳定 handoff；本 Story 只交付质量资格事实，不提前创建或运行规则、候选和线索。
- 让 R6 在 owned-source 范围看到来源、依赖、组合算子、失败成员和水位；一个来源 eligible 绝不能显示成整条规则 eligible。
- 本 Story 是 FR-12/NFR-10 的阶段性 enabler，不声明关闭“熔断后新正式线索数=0”或生产持续时长指标。

## Story 元数据与实施边界

- **唯一硬依赖：** Story 2.3；间接继承 Story 2.1 的 17 个 source、11 个稳定 dependencyId 和 DCC 历史锁。Story 2.5a-c、3.1b/c、3.2、3.4、4.1a 是消费者而非前置。
- **领域所有权：** `ingestion-quality` 唯一写最小 `RuleDependencyRegistry` 投影、dependency cursor/state 和 `QualityEligibility`。`rule-governance`、`signal-evaluation`、`clue-care` 只能在后续 Story 经公开事实/port 消费；禁止跨模块内部 import 或直写别域表。
- **输入真实性：** 仅消费 Story 2.3 已锁定且 self-contained 的 quality-assessed/published 事件，并从同一 owner 的不可变 `QualitySnapshot` 行取得完整证据。当前冻结事件和 42-field HTTP projection **没有** QSHM version/digest；2.4 必须用 event 的 snapshot identity/hash 精确定位 owner-local snapshot，校验后复制 `snapshotId + immutableHash + QMDP version/digest + QSHM version/digest`，或先发布兼容 event successor。禁止假定旧 wire 字段存在、原位修改旧 lock、重算 QMDP 指标或 QSHM preimage/hash。
- **发布前置：** `quality-assessed=passed` 的 batch v3 尚未发布 normalized facts，不能产生 eligible；只有匹配的 `data-batch.published` v4 可参与 eligible。`quality-assessed=failed` v3 是合法终态，不期待 v4，也不能把“没有 v4”误判为事件 gap。
- **排序边界：** batch `aggregateVersion=3/4` 只在单个 batch 内单调，会在新 batch 重新开始。跨批次必须使用 Task 0 锁定的 sourceVersion/lineage/cursor 规则；禁止按 UUIDv7、occurredAt、watermark 字符串或不同 batch 的 3/4 推断顺序。watermark 是 opaque evidence，不从其日期后缀或 digest 推导业务时间。
- **状态边界：** `eligible/fused/recovering/missing` 是质量资格，不是 RuleVersion governance/runtime 状态，也不是 snapshot result。2.4 owner 模型和事实合同必须能表达三态；本 Story 的生产输入只驱动 `eligible/fused`，`fused→recovering` 由 2.5 的受权恢复流程通过公开 command/port 驱动，2.4 可用 conformance fixture 验证但不得伪报运行闭环。
- **失败边界：** 合法且已 assessed 的质量失败可使受影响 dependency fused；未知/缺失/摘要不匹配的 QMDP/QSHM、无效事件、KMS/DB/audit/outbox/backfill 故障属于 technical failure：隔离或暂停、不推进 cursor、不发布新 eligibility。
- **合同演进：** `contracts/data-catalog/dependency-registry-1.0.0.json` 仅是 11 个身份映射 seed，缺少 RuleVersion 维度和完整组合语义；DCC/RC/QMDP/QSHM、旧 lock、旧 migration 和 release v1-v5 的字节不可改写。新增独立/additive successor、schema、fixtures 和 digest lock。
- **权限边界：** 当前 RFP 可让 R6 以 `Dependency/data-quality.read` 读取 owned dependency；若 API 把 `QualityEligibility` 作为新对象类暴露，Task 0 必须先发布 RFP/field-projection successor。禁止只在 controller 或前端手写 allowlist；R7 技术状态与 R6 业务质量投影分开。
- **证据边界：** 未安装的 rule-domain consumer、2.5 recovery 调用、目标部署和生产持续时长保持 `runtimeEvidenceClaim=none/deferred`；fixture、sandbox 或 outbox 行不能冒充生产闭环。

### 本 Story 包含

1. RuleVersion 依赖注册 successor、QualityEligibility 状态/事件、ordering/backfill、authorization/projection 和 retention 合同及 checker。
2. 对 Story 2.3 assessed/published 事件的持久 inbox、严格交叉绑定、source/dependency cursor、duplicate/old/gap/poison/backfill 处理。
3. dependency 状态与 RuleVersion 组合的确定性计算、不可变资格事实、CAS/idempotency/audit/outbox 原子提交。
4. ACC-SAFE-001/002 的 required all-of 验收，以及全部当前 source-backed RuleVersion 的登记完整性；通用 optional/any-of/threshold 只以合同 fixture 验证，不虚构生产规则。
5. R6 desktop 质量面板中的依赖资格/组合树只读表面，及完整自动化、PostgreSQL、隐私、性能和 additive release evidence。

### 本 Story 不包含

- 创建、修改或发布 RuleDefinition/RuleVersion，改变其 governance/runtime 状态，或实现 rule evaluation、个人基线、Candidate、Clue、任务、通知和学生结论。
- Story 2.5 的熔断任务、冻结新产出、D4 恢复审批、观察窗、回退或恢复任务收敛；仅提供其后续调用的 owner port/事实合同。
- 把 `impactScopeCodes` 解释成 dependency/rule/category；该字段是 QMDP metricId。依赖影响只能通过锁定 registry 映射。
- 为 6 个非规则消费源伪造 dependencyId，为 `CORROBORATE-001` 伪造 source dependency，或把 SPM-1.0.0 当成第七条 RuleVersion。
- 修改 QualitySnapshot/hash material、原位改 DCC/RC/registry/QMDP/QSHM/历史 lock/migration/release，或新增/升级依赖。
- 移动端复杂质量表面、人工 pass/fuse/eligible 开关、从页面直接发布 eligibility，或缓存业务对象到浏览器持久存储。

## Acceptance Criteria

### AC-2.4-HAPPY：登记、排序与发布（受控原始 AC）

**Given** `RuleDependencyRegistry` 与单调事件版本契约通过测试<br>
**When** 数据责任人执行本 Story 的主流程<br>
**Then** 乱序或间隙暂停推进并补拉；本 Story 不创建 `RuleEvaluation`、`Candidate` 或 `Clue`<br>
**And** 服务端授权、失败可见、审计、幂等和 `aggregateVersion` 冲突路径必须通过自动化或可复现验收。

### AC-2.4-COMPOSITION：required all-of 失败关闭（受控原始 AC）

**Given** DEC-012 中每个被 RuleVersion 消费的 sourceId 已映射到稳定 dependencyId，非规则消费源只保留 sourceId/purpose 合同，且 RuleVersion 声明 required/optional 与组合算子<br>
**When** ACC-SAFE-001 出现校门 eligible 但宿舍门禁 fused，或 ACC-SAFE-002 出现宿舍门禁/校历/课表/设备任一 required 依赖 `fused/recovering/missing`<br>
**Then** required all-of 组合不得发布 eligible；只有每个 required 依赖均 eligible 且版本连续时才发布对应 `QualityEligibility=eligible`<br>
**And** 事实保存 source/dependency version、组合算子、失败成员和水位，供 G-03 契约测试复现。

### AC-2.4-REGISTRY-CONTRACT：现有 RuleVersion 的依赖注册完整且不可臆造

**Given** DCC-1.1.0、DEC-012、RC-1.0.0 和现有 dependency-registry-1.0.0<br>
**When** Task 0 生成 additive RuleDependencyRegistry successor<br>
**Then** registry 只能引用 RC-1.0.0 已存在的 `ruleId/ruleVersion` 和 11 个稳定 dependencyId，并锁定 `registry/catalog/ruleCatalog versions+digests`、source/dependency identity+version、composition group、required/optional、`all-of|any-of|threshold` 及 threshold 参数、owner/approval/effective evidence 和 canonicalization profile<br>
**And** 生产注册完整覆盖 ACC-SAFE-001 的 7 个、ACC-SAFE-002 的 6 个、ECON-012 的 4 个、NIGHT-001 的 4 个、ACADEMIC-001 的 3 个 required all-of 依赖；`CORROBORATE-001` 无直接 source dependency，SPM-1.0.0 不增加 dependencyId<br>
**And** schema/checker 必须拒绝未知/重复 source、dependency、rule/version、非规则消费源映射、未定义组合、threshold 缺失/越界、版本/digest 漂移和不完整生产注册；通用 optional/any-of/threshold 可用 synthetic fixture 验证，但不能写入生产 RC-1.0.0 实例或声称生产规则已使用<br>
**And** 旧 dependency-registry-1.0.0、DCC/RC 和 lock 字节保持不变；现有 `DependencyBinding` 可扩展/适配，但不得并行建立第二套稳定 identity 目录。

### AC-2.4-UPSTREAM-INTEGRITY：只接受 2.3 的真实、完整且已发布 handoff

**Given** 一个 Story 2.3 quality-assessed 或 data-batch.published 事件，以及由其 snapshot identity/hash 精确定位的 owner-local 不可变 QualitySnapshot<br>
**When** consumer 校验 envelope、event type/schema、batch/source identity、batch v3/v4、snapshot aggregateVersion、status/result、manifest/watermark/lineage，并把事件证据与 snapshot 行的 QMDP/QSHM 绑定交叉校验<br>
**Then** assessed-failed(v3) 可驱动匹配 dependency fused 且永不等待 v4；assessed-passed(v3) 只记录待发布证据、不发 eligible；只有同一 batch/snapshot 的 published(v4) 与 v3 证据严格匹配后才参与 eligible<br>
**And** consumer 验证并传递 `snapshotId/immutableHash/QMDP version+digest/QSHM version+digest`，保留 registry/catalog/rule versions、sourceVersion、manifest、cutoff/observation/effective time 和 opaque watermark；当前旧事件缺少的 QSHM refs 只能由精确 owner-local lookup 或锁定 successor 补齐，不得重算 QMDP/QSHM、宽松 lookup latest 或把 `impactScopeCodes` 当依赖影响范围<br>
**And** 任一 required 输入未知、缺失、额外、摘要不匹配或交叉绑定无效即 poison/technical error：业务状态和 cursor 不推进，不写 fused/eligible，不污染质量趋势；错误原因可诊断且不含学生明文。

### AC-2.4-ORDERING-RECOVERY：跨批次单调性、间隙和更正可重放

**Given** 同一 source/dependency 的 duplicate、old、gap、poison、迟到或 correction/successor 事件序列<br>
**When** inbox consumer 尝试推进 dependency cursor 与 RuleVersion 组合<br>
**Then** `(source,eventId)` 重复幂等，旧 sourceVersion/lineage 不覆盖新状态；gap 持久化为 paused 并请求受控 replay/backfill，poison 隔离告警且 cursor 不推进；补齐后按锁定顺序确定性恢复<br>
**And** Task 0 必须锁定跨 batch 的业务序列键、合法 successor/correction、failed-v3 终态、passed-v3→published-v4 配对、backfill request/response、retention-expired/unrecoverable 语义和 eligibility business key；不同 batch 的 aggregateVersion 3/4 不得作为 source 序列<br>
**And** source/dependency cursor、inbox、quarantine/backfill state、eligibility state、local audit、outbox 与 idempotency 在 owner 本地事务中按对应命令全成或全败；DB/CAS 冲突返回稳定 409，不出现部分推进或静默跳 gap。

### AC-2.4-ELIGIBILITY-FACT：组合事实确定、自足、单调且可供下游复现

**Given** registry 中某 RuleVersion 的全部当前 dependency 状态和连续 cursor<br>
**When** composition evaluator 计算新的 QualityEligibility<br>
**Then** required `missing|fused|recovering|版本不连续` 均 fail closed；all-of 仅全部 required eligible 时 eligible；optional 不得掩盖 required failure；any-of/threshold 严格按锁定 contract 计算并以边界 fixture 验证<br>
**And** eligibility 事实至少保存 `eligibilityId/businessKey/aggregateVersion/status/reasonCode`、ruleId/version、registry/catalog versions+digests、operator/threshold、每个 member 的 sourceId/sourceVersion/dependencyId/dependencyVersion/state、failedMembers、source/dependency watermarks、snapshot lineage/hash references、effectiveAt/occurredAt/traceId/producer<br>
**And** 同业务键同 body 重放返回原结果；同键异 body、旧 expectedAggregateVersion 或内容漂移失败。更正产生新 aggregateVersion/事实，不 update/delete 历史事实；source aggregate 不携带无归属 `deliveryStatus`<br>
**And** 事实经 transactional outbox 发布为自足、版本化 CloudEvent，`source+id` 唯一、owner aggregateVersion 单调，≤64 KiB；duplicate/old/gap/poison/backfill fixtures 可让 Story 3.2 重放同一结论，未安装真实 consumer 时 `runtimeEvidenceClaim=none`。

### AC-2.4-AUTH-AUDIT-PRIVACY：R6 只读最小投影且授权失败关闭

**Given** R6/R7、owned-source evidence、当前 policy/objectVersion/identity generation 和读审计依赖<br>
**When** 查询 dependency composition/eligibility 列表或详情，或 workload 消费上游事件<br>
**Then** R6 仅以现有 `Dependency + data-quality.read + owned-source` 边界看本人依赖及受影响 RuleVersion 的业务质量最小投影；跨多个 source 的 RuleVersion 只有在每个暴露成员都授权且 projection policy 允许时才显示完整树，否则服务端返回受控 redacted/不可见结果且不通过总数/分页泄漏其他 owner 数据。R7 只见 technical cursor/job/quarantine/trace 投影<br>
**And** API 使用 `/api/v1`、UUIDv7、ISO-8601 offset、`no-store`、显式 pagination/sort 和统一 error envelope；不存在与越权不可区分，授权在查询和序列化前重检，敏感详情按策略先成功写 read audit 再返回<br>
**And** authorization、field projection、owner evidence、read-audit token 与 requested object 在 DB/应用层精确绑定；provider/audit 不可用则失败关闭。事件、DTO、DOM/a11y tree、日志、metric 和 trace 不含学生标识、原始记录或高基数业务文本<br>
**And** workload identity/capability 与 R6 human read 分离；浏览器不能提交 eligibility 状态变化。若现有 RFP/field projection 不能表达对象/字段，必须先发布 additive successor 与 checker，不能靠前端隐藏。

### AC-2.4-DEPENDENCY-UX：依赖树诚实、可访问且不越界实现恢复

**Given** 已授权 R6 在 desktop `data-quality-panel` 查看一个或多个质量快照<br>

**And** 复用 `QualitySnapshotsView.vue` 现有受保护 shell、URL/identity-generation/no-persistence/cache/a11y 约定，替换 Story 2.4 placeholder；Story 2.5 的熔断/恢复动作继续显示 `pending-story-execution/not-available`，不返回空数组、假 eligible 或可点击假动作<br>
**And** 列表/组合树使用物化投影、索引和有界 bulk query，不按成员 N+1 hydration 或在线扫描 snapshot/fact；键盘、读屏、AA、200% zoom、1366/1440 自动验证，`<768px` 不渲染复杂业务表面。

### AC-2.4-EVIDENCE：合同、数据库、性能和 release 声明可复现

### 领域、事务与事件设计约束

- 推荐把 owner 状态分为：`DependencyQualityState`（按 stable dependency + source version/lineage）、`RuleDependencyRegistry`（按 rule/version+registry version）和 `QualityEligibility`（按 rule/version+registry version 的 current/history）。具体业务键/aggregateVersion 在 Task 0 固定后由 Java/DB/schema 共用 golden vectors。
- eligibility 事件是 downstream decision fact，必须复制决定所需快照证据，不能要求未来回读 “latest” QualitySnapshot；snapshot owner retention 为 2 年，eligibility/规则证据 retention 需在 Task 0 映射并保留合法删除 handoff。
- 组合 evaluator 是纯函数；事件消费/application transaction 负责验证、cursor、CAS、audit/outbox。不要让 controller/JDBC adapter 重算组合或把 UI 状态当领域命令。
- 同一 source 可能影响多个 RuleVersion；一次输入可在一个受控事务中更新有界集合，也可按 deterministic business key 分事务，但必须锁定原子边界、重放次序和 crash recovery，避免部分 rule eligibility 可见。
- 使用 persisted inbox/watermark，而不是内存 cursor。事件 delivery at-least-once；relay delivery 状态放独立记录，不写进 dependency/eligibility aggregate。
- 结构化日志只含低基数 code/state 与 opaque ID/traceId；source/dependency/rule 只有在受控小枚举并通过基数门后才可作 label，snapshot/batch/student identity 绝不作 metric label。
