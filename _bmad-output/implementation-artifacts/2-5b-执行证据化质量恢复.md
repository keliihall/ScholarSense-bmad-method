## Story

作为数据责任人，
我希望在完整性和样本验证后恢复规则消费，
以便只有经受控证据、影响预览和 D4 双人复核确认安全的熔断进入恢复观察，且不补发已失效线索。

## 业务与交付价值

- 把“修复完成”从人工判断变为可重放的 QRP 证据包：质量门、连续通过批次、补数/全量对账、分层样本、版本水位和影响范围必须一致。
- 为 `quality-fuse.recover` 落地真实 D4 职责分离：数据 owner maker 与业务 owner checker 为不同自然人；审批、权限、对象、策略或作用域漂移即失效。
- 只在 `ingestion-quality` 单写入者事务中将真实 active fuse episode 从 `fused` 转为 `recovering`；成功表示“已进入恢复观察”，不是 eligible/production。
- 对过时窗口只形成“修复历史证据、不补发”的版本化 handoff，不创建 RuleEvaluation、Candidate 或 Clue。
- 向 Story 2.5c 交付自足 observation handoff；真实规则消费激活仍归 3.2，公共任务最终 apply/关闭仍归 5.5。

## Story 元数据与实施边界

- **开工基线：** 当前 `main@017997a` 只合并到 Story 2.3；Story 2.4/2.5a 是工作树中的已验证候选，2.5a 的 17 条 review findings 已闭合。实施前记录 exact commit/tree/工作树候选；禁止 checkout/reset 或按 HEAD 重建、覆盖现有改动。
- **单一 owner：** `ingestion-quality` 继续是 `QualityEligibility`、active `QualityFuseEpisode` 和 owner-local `RecoveryTask` 的唯一写入者。复用同一 episode/task/eligibility，不建立第二套 recovery truth。
- **状态结果：** 本 Story 唯一质量状态迁移是 `fused -> recovering`。`recovering -> eligible`、完整 observationDuration、24h 复发回退、episode/task 关闭归 2.5c；2.5a 的 latch 矩阵必须保持回归。
- **两阶段 D4：** 2.5b 保存 D4 恢复计划证据并在 15 分钟 execution token 有效期内原子进入 recovering；2.5c 观察满足时重新验证持久审批证据与当前条件并取得新的执行确认。不得复用或静默延长 2.5b token。
- **QRP 固定值：** 流式源连续 3 批通过、观察 60 分钟；日批源连续 2 批通过、观察 24 小时；补数起点 `max(lastKnownGoodWatermark, trustedNow-90d)` 并全量对账；分层重算至少 100 个 subject-window，总体不足时全部，`mismatch=0`。不得从 DCC frequency、UI 或默认值猜流式/日批。
- **样本重算：** QRP 重算不是 Story 2.2 的 `MappingRecomputeJob`，也不允许 ingestion-quality 伪造 RuleEvaluation。必须冻结 `RecoverySampleRecomputePort` 的 producer/consumer 和无 PII 摘要合同；真实 provider 未安装时 runtime fail closed/`none`，fixture 不能让对象进入 recovering。
- **D4 边界：** RFP 允许 R6 对 owned-source RecoveryTask 发起恢复，不等于 D4 已通过。maker 是当前数据 owner，checker 经 runtime business-owner binding 决定；二者必须为不同自然人且禁止自审，不得把 R3 或任何静态角色写死为 checker。HRAP 的固定输入还必须保存 actionType、actor、authorization context、impact scope、data sensitivity、current/target state、reason、matrixVersion 和 policyVersion。
- **授权实缺：** `AuthorizationObjectEvidence.highRiskApprovals` 可被 CompositeAuthorization 消费，但仓库尚无共享 D4 生命周期服务，也无支持 `RECOVERY_TASK` 的生产 `AuthorizationObjectEvidenceProvider`。Architecture 要求统一 HRAP 门禁，却未在核心 owner 表中唯一指定 approval/receipt/token 的写 owner；Task 0 必须先通过受控 Architecture successor 明确其唯一 owner、事务边界、公开 port、跨模块协作、token consumption owner 与原子执行协议，不能预设某个模块。owner/协议未冻结即 HALT；不得在 `ingestion-quality` 复制 action-local HRAP evaluator。只为已通过本 Story七路径的 `quality-fuse.recover` 启用 runtime actionType；还必须安装唯一 RecoveryTask owner provider，不得回显 expectedObjectVersion、接受客户端 highRiskApprovals 或仅在 UI/controller 判断。
- **过时窗口：** 2.5b 尚无真实 `recoveryCompletedAt`。preview 按 RuleVersion/window 分为已过期、当前仍可能可行动、预计观察完成前过期；2.5c 用真实完成时间最终重算。2.5b 不恢复或补发窗口。
- **业务边界：** 不创建 RuleEvaluation/Candidate/Clue，不修改 RuleVersion governance/runtime，不激活公共任务 target，不把 `TaskDelivery.confirmed` 当恢复完成，不把六条 `approved+inactive+fused` bootstrap 规则借 API 变成 eligible/production；只处理 2.5a 真实 active episode/open task。
- **证据分层：** schema/fixture、DB 行、deployment profile、HTTP 2xx、transport ack 或可重复制品不是生产恢复证明。2.5b 完成必须安装真实 `RecoverySampleRecomputePort` provider 与 Task 0 冻结的 HRAP runtime owner，并以正向 request -> worker -> D4 -> owner transaction 证据证明真实 `fused->recovering`；provider-not-installed 只能作为负向 fail-closed 证据。只有 2.5c observation/eligible、3.2 consumer、5.5 final apply 和 production-duration 可保持 deferred/`runtimeEvidenceClaim=none`。

### 本 Story 包含

1. QRP executable policy、recovery request/approval/evidence/impact preview/job/handoff/retention 的 additive 合同、fixtures、digest locks 与 checker。
2. 完整性、连续批次、90 日补数起点、全量对账、分层样本摘要和 impact preview 的持久化校验编排。
3. Task 0 通过 Architecture successor 冻结的 HRAP 公共边界中的 D4 pending/approved/rejected/expired/cancelled、maker/checker 分离、4h pending、15min single-use token，以及 ingestion-quality 对受信 receipt 的重检和按冻结原子协议完成 execution authorization/token 消费。
4. 单一最终 recovery command port 和 owner-local 原子事务：eligibility、request/evidence、episode/task、audit、event/outbox、owner-local execution-jti/幂等响应全成或全败；跨 owner HRAP token 的消费按 Task 0 冻结的原子协议执行，不得假设可加入该事务。
5. R6 desktop 证据/D4 流程，以及 contract/domain/MVC/JDBC/PostgreSQL 18.4/授权/隐私/UI/release 证据。

### 本 Story 不包含

- `recovering -> eligible`、观察完成/回退、episode/task 关闭或恢复 production（2.5c）。
- 真实 signal-evaluation consumer 和生产零新业务对象的最终验收（3.2）；公共任务 target/final apply（5.5）。
- 复用主体映射重算表/作业作为 QRP 重算、从 latest 拼证据，或按 UUID/occurredAt/watermark 猜连续批次。
- 修改 V000015/V000016、2.5a 已锁合同/release v1-v7/PAB/dependency locks，或升级依赖。
- 移动端复杂质量页、持久化 recovery draft/token/preview、自动重提命令或用 Toast 伪装持久成功。

## Acceptance Criteria

### Epic 原始七条 AC（canonical，逐字保留）

**AC-2.5b-HAPPY** — **Given** approved QualityRecoveryPolicyVersion 明确质量阈值、consecutivePassedBatches、observationDuration、样本重算集合/预期、latestActionableAt、审批角色和失败回退；**When** 具权人员申请恢复；**Then** 依次满足质量阈值、连续通过批次、样本重算预期、影响预览和 D4 双人复核后进入 recovering；**And** 只保留满足 `recoveryCompletedAt ≤ latestActionableAt` 的仍可行动窗口；完成恢复晚于 latestActionableAt 的窗口直接失效且不补发，eligible 必须等待 Story 2.5c 的完整观察期。

**AC-2.5b-AUTH-DENIAL** — **Given** 申请人无 quality-fuse.recover 权限或审批过期；**When** 提交恢复；**Then** 返回不泄露细节的拒绝并保持 fused；**And** 记录 actor、policyVersion、对象版本和 traceId。

**AC-2.5b-ILLEGAL-STATE** — **Given** 质量仍 failed 或规则依赖仍不合格；**When** 尝试跳过 recovering；**Then** 拒绝迁移且不发布 eligible；**And** 显示缺失证据。

**AC-2.5b-BOUNDARY** — **Given** 连续通过批次数、质量值或 latestActionableAt 恰在策略边界；**When** 执行恢复审批与样本重算；**Then** 按 QualityRecoveryPolicyVersion 的含边界定义得到可复现结果；**And** 任一低于或晚于允许边界的结果保持 fused。

**AC-2.5b-DEPENDENCY-FAILURE** — **Given** 样本重算、审批或公共任务依赖不可用；**When** 恢复流程执行；**Then** 保持 fused/recovering 且创建可见失败；**And** 不得降低门槛继续生产。

**AC-2.5b-IDEMPOTENCY** — **Given** 同一 recoveryRequestId 重放；**When** 再次提交；**Then** 返回原结果且不重复审批或事件；**And** 审计关联同一业务键。

**AC-2.5b-CONCURRENCY** — **Given** 恢复期间矩阵版本或质量水位变化；**When** 提交最终确认；**Then** 以乐观锁拒绝并返回最新版本；**And** 用户必须重新预览影响。

以下 AC 将 canonical 意图投影为可实施约束；如措辞看似冲突，以 canonical AC 和“2.5b 只进入 recovering、2.5c 用真实 recoveryCompletedAt 最终筛选”的权威裁决为准。

**Given** 批准文本已定义 QRP-1.0.0/HRAP-1.0.0，但仓库尚无 machine-readable QRP、D4 生命周期和 RECOVERY_TASK owner evidence provider<br>

**Then** 合同唯一确定 source class/阈值/批次序列/观察目标/补数/对账/分层样本、request/approval/execution 状态、maker/checker runtime binding、4h/15min、preview 失效、evidence/job/handoff/retention/error/event 语义<br>
**And** 旧合同/lock 字节不变，未知策略/摘要/provider/actionType 失败关闭；任一语义仍不唯一时 HALT/correct-course。

### AC-2.5b-HAPPY：证据和 D4 满足后只进入 recovering（原始 AC 的实施强化）

**Given** approved `QualityRecoveryPolicyVersion` 明确质量阈值、`consecutivePassedBatches`、`observationDuration`、样本重算集合/预期、`latestActionableAt`、审批角色和失败回退<br>
**When** 具权人员对 2.5a 真实 active episode 申请恢复<br>
**Then** 依次满足质量阈值、连续通过批次、补数/全量对账、样本重算预期、影响预览和 D4 双人复核后，在 owner-local 事务中进入 `recovering`<br>
**And** 2.5b 只以 trusted serverNow + observationDuration 形成版本化 preview/handoff，不最终保留、失效或补发窗口；2.5c 以真实 `recoveryCompletedAt` 执行 `<= latestActionableAt` 最终筛选，晚于上限者只修历史证据，且 `eligible` 必须等待完整观察期。

### AC-2.5b-AUTH-DENIAL：无权、过期或漂移均隐藏拒绝（原始 AC 的实施强化）

**Given** 申请人无 `quality-fuse.recover` 资格、对象不在 owned-source、审批/token 过期，或执行前策略、授权、scope、对象/approval version 已变化<br>
**When** 申请、审批或提交恢复<br>
**Then** 返回与对象不存在一致的无细节拒绝；尚未完成恢复提交的对象保持 `fused`，不因拒绝创建任何部分迁移<br>
**And** 最小拒绝审计记录 actor/action/policyVersion/objectVersion/traceId/result，不泄露对象、成员、审批人或分页细节。

### AC-2.5b-ILLEGAL-STATE：缺失证据不得跳过 recovering（原始 AC 的实施强化）

**Given** 质量仍 failed、required dependency 不合格、对账/样本未通过、不存在 active episode/open task，或目标是 bootstrap `approved+inactive+fused` 规则<br>
**When** 尝试跳过 `recovering`、直接发布 eligible 或恢复 production<br>
**Then** 拒绝迁移且不发布 eligible/RuleEvaluation/Candidate/Clue<br>
**And** 已授权界面显示结构化缺失证据，未授权请求不显示细节。

### AC-2.5b-BOUNDARY：阈值、批次、样本和时间边界可复现（原始 AC 的实施强化）

**Given** 连续通过批次数、质量值、样本数/mismatch 或 `latestActionableAt` 恰在策略边界及精确相邻样本<br>
**When** 执行恢复证据判定、样本重算与审批<br>
**Then** 2.5b 按 exact QRP version/digest、含边界符号、trusted microsecond time 和业务批序列得到可复现 qualification 与 preview 分类；质量值/连续批次低于边界保持 fused，preview 输入漂移即失效<br>
**And** 流式 2/3/4 批、日批 1/2/3 批、总体不足时全取/总体超过 100 时至少取 100、mismatch 0/1、`max(LKG, now-90d)` 两分支有锁定 vector；`recoveryCompletedAt == latestActionableAt` 可行动、晚 1µs history-only 的最终筛选由 2.5c 验收。

### AC-2.5b-DEPENDENCY-FAILURE：技术故障不降低质量门（原始 AC 的实施强化）

**Given** 样本重算、补数/对账、审批/授权/trusted-time 或公共任务依赖不可用<br>
**When** 恢复流程执行<br>
**Then** 保持当前 `fused|recovering` 并产生可见、可诊断、无 PII 的持久失败；不得把 unavailable 解释为 mismatch=0 或 approval passed<br>
**And** 不降低阈值或继续生产；外部任务 I/O 仅在 owner 事务提交后经 TaskDelivery/outbox 发生，运输失败不回滚本地事实。

### AC-2.5b-IDEMPOTENCY：请求、审批与执行全链路幂等（原始 AC 的实施强化）

**Given** 同一 `recoveryRequestId`/Idempotency-Key 和同一 canonical request digest 重放<br>
**When** 再次发起、审批、执行或 worker 重试<br>
**Then** 返回原结果且不重复审批、样本作业、history、event、outbox 或 token consumption<br>
**And** 审计关联同一业务键；同键异 body/digest 稳定 409，不覆盖原请求/结果。

### AC-2.5b-CONCURRENCY：预览后漂移必须重做预览（原始 AC 的实施强化）

**Given** 恢复期间 member set/RuleVersion 矩阵、QRP/HRAP/RFP version、quality watermark、episode/task/eligibility objectVersion、approval 或 authorization generation 变化<br>
**When** 基于旧 preview/expectedAggregateVersion/token 提交最终确认<br>
**Then** 按稳定锁序重读当前事实，CAS 拒绝并返回最小 `currentVersion` 和可重试状态；只有调用方仍有对象权限且字段投影允许时才显示最新操作者代理值/时间，否则不返回<br>
**And** 用户必须重新读取事实、重做 preview 并显式再提交；系统不得自动重放高风险命令。

### AC-2.5b-EVIDENCE-PACK：恢复证据自足，不读 latest 补齐（派生）

**Given** recovery request 经完整性、连续批次、对账和样本验证<br>
**When** 生成 evidence pack 和 readiness decision<br>
**Then** 精确绑定 eligibility/episode/task/generation、全部 RuleVersion/member set、batch/snapshot/hash、source/dependency versions+watermarks、registry/RC/DCC/QG/QMDP/QSHM/QRP/HRAP/RFP versions+digests、selection seed/各分层数量/expected-vs-actual mismatch 摘要、reconciliation、trusted times 和 trace<br>
**And** 证据不含学生明文/原始失败行，不在审批/执行时查 latest 重建；摘要、版本或 provider 未知即 fail closed。

### AC-2.5b-D4-LIFECYCLE：复核证据不能由客户端伪造（派生）

**Given** maker 已在 owned-source 中完成当前 preview 并提交 D4 申请<br>
**When** runtime-bound business owner 批准/拒绝/取消，或 pending 超过 4 小时；随后 maker 使用 15 分钟 single-use token 执行<br>
**Then** 审批状态严格为 `pending|approved|rejected|expired|cancelled`，maker/checker 不同自然人且无职责冲突；token 绑定 actor/action/object/scope/data sensitivity/current+target state/reason/QRP/HRAP/RFP/matrixVersion/policyVersion/approval/objectVersion/previewDigest/impactScope/authentication state 且只消费一次<br>
**And** 请求前资格检查与执行时 exact HRAP approval 分离；Task 0 冻结的 HRAP owner 发布/校验受信 receipt，`QualityRecoveryTaskOwnerEvidenceProvider` 只组合当前 task owner facts 与该 receipt 生成 `highRiskApprovals`，不接受客户端 allow/evidence，也不在 ingestion-quality 复制第二套 HRAP evaluator。

### AC-2.5b-VALIDATION-JOB：长耗时校验可恢复且不产生业务对象（派生）

**Given** backfill/reconciliation/sample recompute 不适合跨越一个 HTTP/DB 事务<br>
**When** owner-local durable worker 执行 queued/running/succeeded/failed/cancelled 作业<br>
**Then** 作业采用 lease/fencing/checkpoint/有界重试；输入绑定 request/episode/task/RuleVersions/member set/watermarks/QRP digest/selection seed，输出仅为不可变 reconciliation/sample 摘要<br>
**And** 不复用 `MappingRecomputeJob` 表/语义，不持久化学生明文，不创建 RuleEvaluation/Candidate/Clue；provider 不可用时作业可见失败且恢复门关闭。

### AC-2.5b-IMPACT-PREVIEW：preview 只是版本化证据（派生）

**Given** 当前 RuleVersions 各有 `latestActionableAt`，且 2.5c 观察尚未完成<br>
**When** 以 trusted serverNow、QRP observationDuration 和当前 watermark 生成 preview<br>
**Then** 按 RuleVersion/window 显示 already-expired/history-only、currently-potentially-actionable、expected-to-expire-before-observation-completes，保存 previewDigest 和精确输入版本<br>
**And** preview 不授权执行、不激活或补发窗口；版本/水位/策略/审批变化使其失效，2.5c 使用真实 recoveryCompletedAt 最终重算。

### AC-2.5b-OWNER-TRANSACTION：恢复提交与证据原子化（派生）

**Given** 当前证据、preview、D4 token 和授权全部有效<br>
**When** `QualityEligibilityRecoveryCommandPort` 应用最终命令<br>

### 权威裁决与实施顺序

1. 先保全当前 2.4/2.5a 工作树候选，再执行 Task 0；contract freeze 前不写 DDL 或激活动作。
