## Story

作为数据责任人，
我希望隔离歧义身份并安全重算有效窗口，
以便平台只将可唯一证明的外部标识关联到永不复用的 `StudentRef`，并在映射更正后以追加式 lineage 恢复仍有业务时效的计算，而不串档、不重复产出、不改写历史。

## 业务与交付价值

- 建立 `subject-registry` 首个生产边界：`StudentRef`、外部标识有效期映射、歧义异常、追加式修复与 alias/redirect 读模型。
- 让学号、一卡通、校园网、住宿和门禁等 source-native identifier 经受控映射后统一引用内部主体；单条歧义只隔离对应记录/主体，不将整个数据源误判为失效。
- 为 28/56 日个人基线与规则复盘保留可追溯窗口索引、源版本/水位、映射版本、规则版本与 lineage，不把“长期保留”与“可行动窗口”混为一个概念。
- 交付可持久、可 fencing、可幂等重放的映射修复重算请求/作业契约，为 Story 3.3a 及后续 `signal-evaluation`/`clue-care` consumer 提供唯一输入真相。
- 让 R6 数据责任人在 owned-source 修复 purpose 下看到最小必要标识、影响窗口与作业结果；R7 仍只见技术状态和 `traceId`。

## Story 元数据与实施边界

- **唯一硬依赖：** Story 2.1；当前 `HEAD@0c759bb` 已包含已完成的 DCC/QG 目录能力与 V000010/V000011。Story 2.3 是 FR-13 contributor，但不是 2.2 的前向硬依赖。
- **需求所有权：** 本 Story 是 FR-10 full owner、FR-13 planning/data-side owner，并是 Story 3.3a 的硬前置。FR-13 runtime 采用 staged closure：本 Story 只关闭窗口、重算意图和 consumer conformance；真实 evaluation supersede、Candidate/Clue 去重及 consumer watermark 由 Story 3.4/3.5 和后续 correction consumer Story 验收，在此之前不得把 FR-13 标记为 runtime full。
- **Epic 2 释放边界：** 本 Story 不创建 `RuleEvaluation`、`CandidateAdmissionDecision`、`Candidate`、`Clue` 或关怀待办，不得用 fake consumer/fixture 宣称下游生产闭环已完成。
- **映射所有权：** `subject-registry` 唯一写 `StudentRef`/`SubjectMapping`/映射异常及更正事件；`ingestion-quality` 仅通过公开端口/事件使用当前映射，并拥有它自身的历史窗口投影与重算作业状态。
- **冻结合同边界：** 当前 `DCC-1.0.0/QG-1.0.0` 不可原位增加 required 字段或改 digest。`studentRef`/`subjectRef` 混用和 source-native identifier 缺失必须由版本化适配/规范化合同解决；如改受控 source schema，发布明确 successor/新 major，不改写 1.0.0。
- **两类重算严格分离：** 本 Story 处理“主体映射修复后的有效窗口重算”。QRP-1.0.0 的 90 日补数、100 subject-window 抽样、D4 maker/checker 和 recovering/eligible 只属于 Story 2.5b/2.5c 质量恢复，不得自动套用到本 Story。
- **有效窗口失败关闭：** 重算选择器必须从版本化规则/场景合同读取 `latestActionableAt` 或等价有效边界，并在发布结果前重检。该边界不存在/不可用时只保留映射更正事实，不推断“永不过期”也不创建重算工作。
- **保留边界：** RS-1.0.0 的规范化事实保留期为 1 年；PP-1.0.0 的 60 日只是性能热工作集，不触发删除或裁剪；DCC 的 90 日只是源补数能力，QRP 的 `now-90d` 只用于质量恢复，均不是主体映射重算范围。本 Story 不引入 84 日默认值；28/56 日是计算窗口，是否重算只由已批准 Rule/场景 actionable boundary 决定，且不宣称 Story 6.6 的 legal hold/DeletionReceipt/备份销毁已验收。
- **估算校准：** 上游 `5d` 未覆盖 `subject-registry` 首次生产实现、时态并发约束、密文标识、异步作业、OpenAPI/事件/页面、PostgreSQL clean+upgrade 与 release successor；建议 `8-12d`。如容量仍限 5d，先 correct-course 拆分，不得删除安全、证据或并发门。
- **ready-for-dev 解释：** 按 create-story 状态机，当前状态只授权执行 Task 0 readiness closure：把已批准的 AD-4/AD-25 和学校既定映射语义物化、取得责任方批准并锁定；不得由开发者自行发明权威键、匹配优先级、外部标识规范化、merge/split/correction 或重算完成策略。合同锁获批前 Task 1-6 必须保持 blocked；任一项无法从受控来源唯一确定时走 correct-course/批准流程。

### 本 Story 包含

1. source-native identifier → `StudentRef` 映射、时态有效期、歧义隔离、异常队列、追加修复与 alias/redirect 当前投影。
2. 服务端最小化/密文保管的源标识，稳定 `StudentRef`、mappingVersion、lineage、supersedes 与不复用 tombstone/reservation。
3. 支持 28/56 日基线和规则复盘的可追溯历史窗口索引/合同，以及有效窗口重算请求、持久作业、去重与 fencing。
4. R6 owned-source 映射异常查询/修复、最小字段投影、幂等/CAS、原子审计；R7 技术状态隔离。
5. 映射更正事件、重算请求事件、重复/乱序/gap/backfill 消费者 conformance 与水位结果。
6. Web 标识异常/修复表面；影响预览/作业结果仅在 Task 0 的 RFP/field-projection successor 获批后纳入，以及 contract/checker、PostgreSQL 18.4、release 和隐私证据。

### 本 Story 不包含

- 基于姓名/证件/联系方式的模糊匹配、概率评分或自动猜测同一人；无 approved 唯一证据即进异常队列。
- DataBatch/QualitySnapshot 计算（2.3）、QualityEligibility（2.4）、质量熔断/恢复（2.5a-c）、RuleEvaluation/PersonalBaseline 计算（3.3a）或 Candidate/Clue 产出。
- 原位把历史事实/证据/线索从旧 `StudentRef` 搬到新 `StudentRef`，或把一对多 split 强行压成单值 redirect。
- 修改 RFP-1.0.0 角色/动作或把映射修复错误提升为 `quality-fuse.recover` D4。
- 将原始学号、卡号、网络账号、住宿/门禁标识写入 URL、日志、metric label、trace baggage、业务事件或前端持久化存储。
- 新建通用任务中心、消息总线、缓存、规则引擎，或修改已冻结 release v1-v3/迁移 V000001-V000011。

## Acceptance Criteria

### AC-2.2-HAPPY：唯一关联、歧义隔离与受控重算（受控原始 AC）

**Given** 主体映射、历史窗口、lineage 和重算去重策略获批<br>
**When** 数据责任人执行本 Story 的主流程<br>
**Then** 唯一映射关联，永不复用 `StudentRef`，歧义隔离；修复后只重算仍有效窗口且不改写历史线索<br>
**And** 服务端授权、失败可见、审计、幂等和 `aggregateVersion` 冲突路径必须通过自动化或可复现验收。

### AC-2.2-MAPPING-CONTRACT：只有唯一权威证据能关联主体

**Given** 已发布 DCC 中的学生、一卡通、校园网、住宿和校门/宿舍门禁记录到达映射边界，且学校批准的版本化映射策略已明确各源权威键、规范化算法、精确匹配优先级和冲突语义<br>
**When** 服务端按该合同规范化 source-native identifier 并求当前映射<br>
**Then** 只有一个获批且有效的权威候选时返回单一 `StudentRef`；零候选或多候选、有效区间冲突、版本倒退、撤销链不完整一律创建/更新 `SubjectMappingException` 并隔离该记录<br>
**And** 被隔离记录不得进入 NormalizedFact 可计算投影、RuleEvaluation/Candidate/Clue；其他无关主体和数据源状态不受污染<br>
**And** 映射策略缺失/未批准/版本未知时 fail closed；不实施姓名/联系方式模糊评分，不把第二个源当作第一个源的替代 owner。

### AC-2.2-TEMPORAL-HISTORY：`StudentRef` 不复用且映射历史只追加

**Given** 外部标识可更正、撤销、合并或拆分，并可在不同时间段被权威源重新发放<br>
**When** 新映射事实或修复命令提交<br>
**Then** `StudentRef` 一经发放永不删除/回收/复用；外部标识映射保存 `sourceId + identifierType + protectedIdentifierToken + [effectiveFrom,effectiveTo) + mappingVersion`，同一键的有效区间不得重叠<br>
**And** 合并、拆分和更正只能追加符合 PIC-1.0.0/CloudEvents 的新事实：envelope 固定 `source+id/type/time`，data 至少含 `schemaVersion/contractVersion/aggregateType/aggregateId/aggregateVersion/occurredAt/producer/correlationId/causationId/supersedesId/reason/effectiveAt/lineageId/traceId`；旧事实、证据和已产生业务对象仍引用产生时的 `StudentRef`<br>
**And** 关系至少显式区分 `alias|merged-into|split-into`；alias/redirect 当前读模型必须能表示 `0..n` 目标及“需人工选择”，`split-into` 不得被压成一对一 redirect 或自动选定当前主体。

### AC-2.2-REPAIR-AUTH-AUDIT：映射修复最小授权、幂等且原子审计

**Given** RFP-1.0.0 当前身份/策略、owned-source anchor、`purpose=SUBJECT_MAPPING_EXCEPTION_REPAIR` 和可用的受信时间/审计依赖<br>
**When** R6 读取或使用 `data-quality.repair` 修复映射异常，或其他角色/越 scope 请求同一对象<br>
**Then** 只有 owned-source R6 可在修复 purpose 下查看批准的最小 I 类字段并提交修复；其他 purpose 下 I 类按 RFP masked/hidden，R7 只见技术作业状态、低基数 code 和 `traceId`<br>
**And** 对象不存在与越权使用同一不泄露 status/code/envelope；发送响应前重检 policy/scope/objectVersion/identity generation<br>
**And** 修复命令必须携带 `Idempotency-Key + expected aggregateVersion + reasonCode + sourceWatermark`；幂等作用域固定为 `tenant+actor+commandType` 并按 PIC-1.0.0 保留 90 日（这不是 QRP 补数窗），同键同摘要返回原结果，同键异摘要或旧版本返回 409 并带当前版本/最新操作者/时间<br>
**And** `subject-registry` 的映射更正、异常状态、模块本地重算请求事件 outbox、幂等结果和 `LocalAuditFact` 在一个本地事务全成或全败；`ingestion-quality` 只在该事务提交后消费事件，并在自己的本地事务创建/重放重算作业，不使用分布式事务<br>
**And** 审计 unavailable/backlog 阻断关键命令；KMS/保护密钥不可用时不返回明文、不提交修复，生产完成声明还必须绑定已批准学校 KMS 的真实运行证据。

### AC-2.2-HISTORY-WINDOW：历史窗口可支持 28/56 日基线并可追溯

**Given** 获批源事实、映射版本、水位和未来 RuleVersion/场景窗口输入<br>
**When** 构建或查询个人基线/复盘所需历史窗口<br>
**Then** 数据边界至少可无歧义取得 28 日、56 日及版本化场景窗口，并保存 `subjectRef/windowId/[startAt,endAt)/timezone/sourceVersions/sourceWatermarks/mappingVersion/qualityGateVersions/ruleId/ruleVersion/lineageRunId/inputDigest`<br>
**And** 时间存储为 UTC，业务解释显式保存 `Asia/Shanghai`，窗口为左闭右开，相邻窗口在边界时刻不重复计入<br>
**And** 历史窗口可从受控源版本/水位重建到相同摘要；不依赖页面会话、前端缓存或可变的“当前学生”别名<br>
**And** 按 RS-1.0.0 保留规范化事实 1 年；PP 60 日只用于性能工作集，DCC/QRP 各自的 90 日语义不裁剪映射历史或扩大本 Story 重算范围；删除/legal hold 最终验收仍属于 6.6。

### AC-2.2-RECOMPUTE：只重算仍有效窗口并以 lineage 去重

**Given** 一次获授权的映射修复产生 correction lineage，且可取得受控 RuleVersion/场景的窗口与 `latestActionableAt`<br>
**When** 服务端生成重算计划并由 worker 执行<br>
**Then** 只纳入修复影响且在服务端受信时钟下仍可行动的窗口；结果发布前再检 `latestActionableAt`，途中过期时只保留 correction/历史证据，不发布新业务工作<br>
**And** 重算工作唯一键至少绑定 `correctionLineageId + StudentRef + ruleId + ruleVersion + scenarioId + windowId + inputWatermarksDigest`；同键同输入重放原结果，同 lineage 下的不同窗口不得被误合并，新水位/新 correction 产生 successor<br>
**And** 作业状态为 `queued→running→succeeded|failed|cancelled`，重试递增 `attemptNo`，租约使用单调 `fencingToken`；检查点、业务写入和结果发布都拒绝过期 worker<br>
**And** 事件消费者对重复幂等、拒绝旧 `aggregateVersion`、对 gap 暂停并补拉，以所有已注册 consumer watermark 到达 correction event 且对账通过作为 correction completed 判据。

### AC-2.2-HISTORY-IMMUTABILITY：重算不改写旧评估、候选或线索

**Given** 历史中可能已存在引用旧 `StudentRef` 的事实/评估/候选/线索，而当前 Epic 2 还没有生产下游 consumer<br>
**When** 执行映射更正和重算 conformance<br>
**Then** `subject-registry` 只发布 immutable correction/recompute request，`ingestion-quality` 只管理受影响数据窗口/作业；两者都不保存或直接更新下游模块的表<br>
**And** 未来 `signal-evaluation` 必须新建 evaluation 并把旧 evaluation 标记 superseded，`clue-care` 必须追加证据更正/人工复核任务，不改写已产生 Clue 历史，Candidate 去重沿用 lineage<br>
**And** 本 Story 必须交付版本化 consumer conformance fixtures 和未来 owner 水位注册点，但将 `runtimeEvidenceClaim` 保持为 `none`，直到真实 owner consumer 实施并在对应 Story 中通过。

### AC-2.2-PRIVACY-UX：标识异常和重算结果最小化、可访问且不伪成功

**Given** R6 从 Web 的标识异常列表进入某 owned-source 异常，或 R7/无权用户访问相同路由<br>
**When** 用户筛选、查看影响、修复、碰到 409/依赖失败，或查看异步重算结果<br>
**Then** R6 的 `SubjectMappingException` 投影严格限于当前已批准字段 `exceptionId/status/subjectOfficialRef/exceptionCode/sourceSystem/sourceOwner/detectedAt`，其中 I 类仅在 RFP 的 `SUBJECT_MAPPING_EXCEPTION_REPAIR` 授权语义映射到字段投影的 `subject-mapping-repair` purpose 且 owned-source 成立时 clear；`evidenceBody/keyValue` 连键都不得出现<br>
**And** mappingVersion、影响窗口/规则数、watermark、修复原因和作业状态若需展示，必须先进入批准的 object schema/policy successor，并按各自对象授权投影；不得借 DTO 临时加字段绕过 RFP/field-projection lock，也不显示关怀结论或原始源报文<br>
**And** loading、empty、filter-empty、error、forbidden、degraded、conflict 和 completed 状态分开表达；状态用文字+图标/结构，键盘、焦点、错误摘要、live region 和 200% 缩放通过<br>
**And** 错误/409 保留当前进程内草稿并显示唯一可执行下一步；成功显示新状态、作业号与结果入口，不只 Toast“成功”<br>
**And** 作业脱离页面会话，只通过所属领域作业状态页/现有公共待办深链返回；不建通用任务中心，不把学生/映射/异常/草稿写入 localStorage、IndexedDB、Cache Storage、Service Worker 或持久 Pinia。

### 实现不变量与复用顺序

1. 先物化 canonical ID、源字段适配、时态唯一、异常状态、lineage、窗口键和错误 oracle，再写领域/持久化/UI；不从代码反推合同。
2. `domain ← application ← adapters`；跨域只经 `<module>.api`/版本化事件，当前投影可重建但 owner 事实不共享写入。
3. 映射唯一性以 approved authority+version 为准，不使用概率匹配、不用后来 alias 改写历史、不用一个源 eligible 代替另一个源。
4. 密文与 deterministic token 可轮换且绑定 keyRef/keyVersion；搜索 token 不是学生业务 ID，不得输出到 API/事件/日志。
5. 映射更正只在 `subject-registry` 本地聚合事务内原子提交 current projection、exception、correction/recompute-request outbox、idempotency 和本地审计；`ingestion-quality` 在提交后消费，并在独立本地事务原子提交 inbox 去重、job/checkpoint 和自身审计/outbox，绝不跨模块共享事务或写表。
6. 重算键必须区分主体、规则版本、场景、窗口、输入水位和 correction lineage；只用 `lineageId` 会错误合并多窗口。
7. 作业必须持久、无会话、可断点恢复；取得租约、每个 checkpoint 和发布结果都校验 fencingToken，cancelled/过期 worker 不得提交。
8. 事件为自足事实快照；同聚合严格 `watermark+1`，duplicate 幂等，gap 暂停/补拉，poison 隔离告警，版本破坏性变更升 major。
9. 日志/metric/trace 只记低基数 source/result/error/job status 和 tokenized object ref；不记外部标识、StudentRef 明文、候选列表、规则影响明细或密钥/密文。
10. 任何 fixture/mock/local PostgreSQL 证据只是 conformance；只有绑定当前 committed candidate/authority/environment/digest 且从实际执行派生的证据可声称 target runtime。

### 技术栈与最新官方约束

- 保持批准基线：OpenJDK 25、Spring Boot 4.1.0/Spring Framework 7.0.8+、Spring MVC/JDBC、pgJDBC 42.7.12、PostgreSQL 18.4、OpenAPI 3.1.2、JSON Schema 2020-12；不新增 JPA、Flyway、Kafka、Redis、Spring Modulith 或新业务库。
- Spring Boot 4.1.0 官方要求 Java 17+并支持至 Java 26，JDK 25 在范围内；不因“latest”升级 PAB。Spring JDBC 继续负责资源释放、异常翻译和事务集成。
- PostgreSQL 18.4 是批准 patch，并修复了 startup packet 无界递归及内存分配整数溢出等安全问题；实际运行环境必须证明 18.4，不用 JDBC 驱动版本代替服务端证据。
- PostgreSQL 18 的 range/multirange、GiST exclusion 和 `WITHOUT OVERLAPS` 可表达非重叠有效期；标量键+范围约束通常需 `btree_gist`。扩展由迁移/部署权限预先供应，online 账号不得获得扩展管理权；exclusion constraint 不能作为 `ON CONFLICT DO UPDATE` arbiter。
- pgJDBC 42.7.12 修复 `channelBinding=require` 可被静默降级的 CVE-2026-54291；保留 2.1 已接入的 TLS/channel-binding/连接身份启动门，不仅在单测中构造 profile。
- JDK 25 `java.util.UUID` 没有 Java 26 才新增的 UUIDv7 `ofEpochMillis`工厂；本 Story 应复用/安全提取现有 `CatalogUuidV7` 的 RFC 9562 字节级实现并做回归，不调用不存在的 JDK API。
- 外部输入全部服务端 allowlist/长度/版本校验，SQL 全参数化；并发冲突由数据库约束、CAS 和稳定 `SUBJECT_REGISTRY_*` 错误同时锁定。
