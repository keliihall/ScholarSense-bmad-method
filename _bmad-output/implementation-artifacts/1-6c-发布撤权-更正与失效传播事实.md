## Story

作为授权管理员，
我希望错误的账号、角色、组织或辅导员—责任学生关系映射，以及过期、撤销和无效关系，都形成不可变、可追踪、可对账的失效事实，
以便平台提交变更后的下一次敏感请求立即失败关闭，所有已启用下游按连续水位收敛，而历史证据永不被改写。

## 业务与交付价值

- 为关闭 FR-2 交付：权威账号、角色、组织树和责任关系的更正、撤销、失效，不再停留为“同步了当前值”，而是形成可证明的事实链与当前授权结果。
- 为关闭 NFR-27 交付：保留 15 分钟授权生效证据和每日责任关系对账，并将每次更正/撤权追踪到所有已注册下游水位；full runtime closure 仍受下述受控范围决策约束。
- 将两个保证明确分离：当前授权在本地事实提交后立即 fail closed；任务、导出、移动等异步消费者通过 outbox、连续版本和水位最终收敛。异步延迟绝不能延迟当前授权失效。
- 为 1.7、1.8、3.9b、3.14c、5.5 与 Epic 7 提供统一、版本化的失效消费合同，避免各模块自行解析责任表、轮询旧值或创建互不相容的撤权机制。

### Task 1 必须冻结的失效合同

在写生产实现前，提交新的版本化失效合同、JSON Schema、正反 fixtures、checker 和 contract lock，并取得 source owner/Hei 的受控批准。至少冻结：

1. **事件类型与原因：**
   - 受控 `changeKind` 至少包含 `corrected | revoked | expired | invalidated`；
   - 为兼容 Story 3.9b 已冻结的 `responsibility.changed` 输入，默认使用单一 `scholarsense.identity-access.responsibility.changed.v1`，由 `changeKind` 区分 correction/revoke/expiry/invalidation；若批准多 type 方案，必须同时冻结到 `responsibility.changed` 的规范映射/兼容别名；
   - 受控 `reasonCode` 区分直接责任变更、账号停用、R1 任职失效、学院失效、关系到期、完整快照确认缺失和质量 gate；
   - 若保留完整快照/质量 gate 失效，必须同时冻结恢复事实：恢复只能由更高连续 source/reconciliation 证据追加新的 corrected/revalidated 事实，不得删除旧 invalidation 或直接清水位；
   - 不得用自由文本原因驱动授权。
2. **不可变事实链：**
   - `eventId` 标识本次新事实；
   - `lineageId` 在同一权威业务关系链内稳定；
   - `supersedesId` 只指向同 lineage 的直接前一平台事实；根事实为空；
   - 派生批量失效使用 `causeEventId` 指向账号/任职/组织等原因事实，不用一个 supersedes 指针串联不同关系；
   - 链不得跨 lineage、形成 fork/cycle 或回指未来版本；旧事实不可 UPDATE/DELETE。
3. **顺序与水位：**
   - 每个 lineage/业务聚合使用无回滚空洞、单调连续的 `aggregateVersion`，不得发明一个会让无关聚合互相阻塞的全局总序；
   - source version/watermark 与 identity-org/responsibility dependency vector 原样保留，不能由聚合事件版本替代；
   - 消费者水位按 `(consumerId, producer, aggregateType, aggregateId/lineageId)`（或 Task 1 批准的等价隔离路由）保存，只接受该路由的 `currentWatermark + 1`；重复幂等、旧版忽略、gap 只暂停受影响路由并触发 backfill/reconciliation。
4. **事件快照：**
   - 遵循 CloudEvents 1.0.2 和 `contracts/events/envelope.schema.json`；
   - CloudEvents envelope 固定 `specversion/id/type/source/subject/time/datacontenttype`；`data.eventId` 必须等于 envelope `id`，`data` 还包含 `schemaVersion/traceId/producer`、lineage、supersedes、cause、aggregate version、effectiveAt、受控对象 token/digest 和自包含的最小授权失效快照；
   - wire payload 不超过 64 KiB；不得包含姓名、学号、账号、外部 ID 明文、原始 source payload、token 原值、密钥或自由文本。
5. **消费者登记：**
   - 每个 consumer 保存稳定 ID、owner、状态、适用发布版本、是否 required、激活时间与初始水位；
   - `authorization-current-scope`（或批准后的等价 ID）是本 Story 的真实必需消费者；
   - 该消费者精确定义为 identity-access 内的异步 invalidation fence/read-model consumer；source/current 动态查询仍是即时 deny 的第一证据，consumer fence 只收紧并提供传播水位，不能把 1.7 尚未实现的完整 RFP 授权器冒充已完成；
   - 任务、导出及责任转移消费者在其 owner Story 实现前只能是 `planned/not-installed` 且 `runtimeEvidenceClaim=none`，不进入当前版本完成分母，也不得被生产者或测试伪推进；
   - mobile 默认不是独立 consumer：WebView 与 Web 共用服务端 API，对象失权由每请求重算，账号撤销走现有 BFF/IdP session revoke，客户端只承担易失状态清理与后续真机验证；只有批准了真实 server-side mobile projection 后才可登记 mobile consumer；
   - 激活新 required consumer 前必须从批准起始水位回放并通过 reconciliation，不能以“从最新开始”跳过历史。
6. **完成定义：**
   - 对单个失效事件，只有所有“当前发布版本适用、required 且 active”的消费者均将该聚合水位连续 apply 到目标 `aggregateVersion`，且 reconciliation 无 gap/冲突时，才可标记 propagation complete；
   - planned、disabled、quarantined、落后或没有 owner 的消费者必须显式可见，不能显示为通过。

当前 `RESPONSIBILITY-AUTHORITY-1.0.0` 使用 exact-field allowlist，且 relation 没有 `changeKind/reason/effectiveAt/lineageId/supersedesId`。Task 1 的默认决策是新增 `RESPONSIBILITY-AUTHORITY-2.0.0` 并冻结 1.0/2.0 dual-read 与切换窗口，因为新增必填更正语义属于 breaking change。只有 source owner 明确批准“平台依据前后事实稳定分类、平台从首次关系事实建立 lineage”的 provenance 规则时，才可继续使用 1.0 输入并另建输出失效合同。1.0 的 inactive/effectiveTo 可使当前 scope 立即 deny；若不能形成可靠 lineage/reason，不得伪称完整更正传播已完成，而应请求 2.0 replay 或进入受控 blocked。关系自然到期的 `expired` 可由受信时间和已批准的半开区间确定性派生。

当前 `contracts/events/envelope.schema.json` 只是通用 seed：`data` 未绑定业务 schema，type 正则不接受 PIC 的 `scholarsense.` 前缀；`scripts/check_contract_seeds.py` 也会拒绝业务事件所需的结构。Task 1 必须同步演进公共 envelope/引用规则与 checker，保留既有 CloudEvents `specversion=1.0` 和旧 fixture 兼容性；不能绕开公共合同另写一套 JSON。

## Acceptance Criteria

### AC-1.6c-HAPPY：更正、撤权或失效形成不可变事实并传播

**Given** 权威源发布更正、撤销或无效关系版本<br>
**When** 失效事实传播到授权、任务、导出和移动会话<br>
**Then** 发布带 lineage 与 supersedes 的更正/撤权事实，并推进所有下游失效水位<br>
**And** 下一次敏感请求 fail closed，历史事实不改写且异常可按 traceId 对账。

### AC-1.6c-ATOMIC-PUBLISH：本地生效、事实与 outbox 原子提交

**Given** 权威源版本已通过合同、签名、连续性、依赖水位与 fencing 校验，或受信时间使关系到达 `effectiveTo`<br>
**When** identity-access 提交 correction/revoke/expiry/invalidated 变更<br>
**Then** 直接责任变化在同一事务提交 source/current、scope 失效事实、业务 outbox、LocalAuditFact/audit outbox 与该 lineage 的下一 `aggregateVersion`；identity/org 高扇出变化在源事务提交 source/current、cause、持久 impact job 与 audit，后续每个派生 scope 批次各自原子；自然到期不改写 authority source/current 事实，只原子提交 expiry fact、outbox、audit 与 job cursor<br>
**And** 各事务的任一原子成员失败则该事务整体回滚；source/current 或受信时间已证明失权后，下一请求 deny 不等待 impact fan-out、expiry relay 或 consumer ack。

### AC-1.6c-CONTRACT-LINEAGE：合同、事实链与版本语义唯一

**Given** correction/revoke/expired/invalidated 输入或派生事实<br>
**When** normalizer 与失效发布器构造事件<br>
**Then** 只接受 Task 1 批准的 source、schema、contract、event type、reasonCode、lineage 与版本组合；根、直接 supersedes 和 cause 的语义符合合同，事件是自包含、≤64 KiB、无明文标识的 CloudEvents 1.0.2 快照<br>
**And** 缺字段、未知破坏性版本、跨 lineage 指针、fork/cycle、未来 supersedes、同 business key 同版本异 payload 或未批准自由文本原因全部拒绝且零授权/失效水位提交；旧 lock 与旧事实 digest 保持不变。

### AC-1.6c-IMMEDIATE-FAIL-CLOSED：当前授权不等待异步传播

**Given** 平台已经提交账号停用、R1 任职/学院失效、责任关系 inactive/correction/revoke，或 `serverNow == effectiveTo`<br>
**When** 同一或另一节点发起下一次敏感对象请求<br>
**Then** 服务端从当前 identity-org、responsibility、object/policy version 和受信时间重算，不使用前端 role、OIDC 展示 claims、菜单、路由或旧内存缓存，统一返回不泄露对象存在性的拒绝语义并保存最小拒绝审计<br>
**And** relay 停止、远程消费者落后、expiry scanner 尚未运行或传播 reconciliation 未完成，都不能恢复旧 scope；IAM/current projection/可信时钟无法证明当前权限时同样 fail closed。

### AC-1.6c-SLO：权威版本可见到授权生效不超过 15 分钟

**Given** correction、revoke 或 identity/org cascade 已在权威源记录 `sourceVisibleAt`<br>
**When** 平台首次以公共 current-scope/read-back 证明旧 scope 已 deny 或新有效 scope 已可见<br>
**Then** 只以该 read-back 时刻记 `authorizationEffectiveAt`，并证明 `authorizationEffectiveAt - sourceVisibleAt ≤ 15m`；job start、HTTP receive、DB insert、outbox send 或 downstream fan-out watermark 均不得冒充授权生效<br>
**And** correction/revoke/cascade 进入与 1.6a/1.6b 一致的滚动 30 日分子、分母、迟到原因与 replay/compensation 证据；超过边界或 evidence 缺失均使 NFR-27 不达标。

### AC-1.6c-CHANGE-CASCADE：身份与责任变化只失效正确范围

**Given** 直接责任关系变化，或账号、R1 任职、学院组织变化会影响一条或多条当前责任关系<br>
**When** 变更提交并解析受影响 scope<br>
**Then** 直接关系变化在源事务中原子追加对应失效事实；高扇出 identity/org 变化在同一事务中追加 cause fact 和持久 impact-resolution job，再以有界批次、游标、fencing 与 completion watermark 生成每个受影响 scope 的派生事实<br>
**And** 高扇出解析未完成期间，动态当前授权已基于 identity/org 新状态 deny，传播完成状态保持 pending；不得做无界事务扫描、跨模块表写入或因部分 fan-out 失败显示全部完成<br>
**And** 单个责任 scope 失效不终止用户全部 SSO；账号/session revoke 才使用现有远程登出/会话撤销路径。不得创建或改变 StudentRef/SubjectMapping。

### AC-1.6c-CONSUMER-WATERMARK：已启用消费者才可推进传播完成

**Given** 注册表同时含当前 active/required 消费者和未来 planned/not-installed 消费者<br>
**When** 失效事件被 relay、消费和确认<br>
**Then** 每个 consumer 在自己的模块内，将 inbox、业务 apply、apply record、自有 watermark 与 `consumer-applied` outbox fact 同事务提交；identity-access 只幂等消费该 applied fact，更新 producer-observed ack/propagation view，不能直接写远程 consumer 的水位<br>
**And** consumer 只有收到其路由恰好 `watermark+1` 时推进；生产者发送成功、HTTP 2xx、broker 接收、回调到达、重试入队或 fixture 都不能冒充 apply；单事件完成状态取该聚合在所有当前适用 active/required consumer 的真实 applied 水位与 reconciliation，planned/not-installed 不被伪推进且激活后必须回放批准起点。

### AC-1.6c-IDEMPOTENCY-ORDERING：重复、旧版、乱序、gap 与 poison

**Given** 相同 `source+eventId` 重放、同键异 payload、旧 aggregate/source version、乱序版本、连续水位 gap 或 schema 合法但无法应用的 poison event<br>
**When** producer、relay 或 consumer 处理输入<br>
**Then** 同键同 payload 返回原结果且不重复事实、outbox、audit、delivery 或水位；同键异 payload 稳定冲突；旧版不覆盖新 head；gap 只暂停受影响 consumer 并请求 backfill；poison 进入有界重试与隔离而不越过水位<br>
**And** backfill/replay 必须验证范围、digest、起止版本和当前 fencing；任何消费者不得用“跳到最新”或人工改 watermark 清除 gap。

### AC-1.6c-CONCURRENCY-ATOMICITY：双 worker、fencing、版本与回滚

**Given** 两个 source/expiry/impact/relay worker 竞争同一业务键或聚合版本，lease 在长事务期间过期，或聚合 head 在提交前变化<br>
**When** 旧 fencingToken、旧 aggregateVersion 或重复 expiry job 尝试提交<br>
**Then** PostgreSQL 条件更新/唯一约束在提交点拒绝旧 worker；失败 worker 对 current state、fact、lineage head、stream version、outbox、audit、job 和 checkpoint 均为零提交<br>
**And** 任一点故障注入使整个核心事务回滚，回滚不会留下聚合版本空洞；提交后的 relay/consumer 失败保留 outbox 并重试，不回滚已生效的本地 deny。

### AC-1.6c-EXPIRY：时间边界立即拒绝且到期事实最终只产生一次效果

**Given** active 责任关系采用已批准的 `[effectiveFrom,effectiveTo)`，且 `effectiveTo` 已到<br>
**When** 请求到达或持久 expiry worker 扫描到该关系<br>
**Then** 请求路径在 `serverNow == effectiveTo` 即返回无效，不依赖 scanner；expiry worker 以关系业务键、版本、effectiveTo 和 reasonCode 幂等追加失效事实/outbox/audit，并推进其 own job cursor<br>
**And** 停机后的 catch-up 不漏发，两个 scanner 不重复产生效果；若更高 correction/revoke 已 supersede 该版本，旧 expiry job 被识别为 stale 且不形成新的 lineage fork。

### AC-1.6c-DEPENDENCY-FAILURE：依赖故障不制造假授权或假水位

**Given** source/network、workload identity、签名、KMS/config、数据库、audit、受信时间、identity/responsibility current projection、relay 或 consumer 任一不可用<br>
**When** 无法安全证明或传播当前状态<br>
**Then** 变更 ingestion 按既有 retry/quarantine 规则保留真实状态，未提交 source 变更不前移 checkpoint；已提交本地撤权继续 deny，outbox 保留重试，失败 consumer 不前移水位，传播状态显示 pending/failed 而不是 complete<br>
**And** audit/local fact 无法原子保存时关键变更失败；仅外部 relay 不可用时本地已提交撤权不倒退。恢复后从最后连续水位幂等追平并 reconciliation。

### AC-1.6c-TRACE-RECONCILIATION：从 source 到所有适用消费者可对账

**Given** 任一 correction/revoke/expired/invalidated 事实<br>
**When** 技术运维按 traceId、eventId、lineageId 或 aggregateVersion 查询传播证据<br>
**Then** 可从 source fact、当前 head、失效 fact、outbox attempt、delivery、consumer watermark、gap/poison、reconciliation 和 audit 获得一致的最小化链路，不需要读取或修改业务明文<br>
**And** 至少每 15 分钟增量核对失效流与消费者连续水位、每日全量核对 lineage head/current projection/required consumer；lag、gap、fork、orphan supersedes、未完成高扇出和 reconciliation mismatch 均告警且不能标记 NFR-27 达标。

### AC-1.6c-PRIVACY-SESSION-CACHE：失权不能被会话或客户端缓存绕过

**Given** 用户保持 BFF/SSO 会话、刷新页面、换号、WebView 恢复或网络重连<br>
**When** 账号或对象 scope 已失效<br>
**Then** 每次服务端敏感请求仍按当前事实重算；客户端不得以 localStorage、IndexedDB、Cache Storage、Service Worker、持久 Pinia 或文件系统保存业务对象/授权投影，易失状态在登出、换号、刷新/WebView 销毁时清除<br>
**And** 账号撤销可触发会话终止；单个对象 scope 失效后重认证也不能恢复该对象。统一无权限文案不泄露对象是否存在，日志、指标、trace、audit 与错误不含明文个人标识或高基数业务 ID。

### AC-1.6c-DOWNSTREAM-BOUNDARY：合同先行但不伪造未来领域完成

**Given** AC 原文点名授权、任务、导出和移动会话，而这些领域消费者由后续 Story 分期交付<br>

### 关键实现不变量

1. **即时 deny 与异步收敛分离：** current projection/动态查询的本地提交是下一请求失权边界；outbox/watermark 只证明下游收敛。
2. **追加而非改写：** correction/revoke/expiry 都是新事实；旧 source fact、失效 fact、audit 与 delivery 证据不可更新删除。
3. **顺序有两层：** source/dependency vector 证明权威输入连续；每个 lineage 的 `aggregateVersion` 证明平台失效事实连续。任何一层都不可被另一层替代。
4. **消费者只在 apply 后 ack：** producer commit、relay send、transport ack 与业务 apply 必须是不同状态。
5. **高扇出有界：** identity/org cause 在源事务持久化，影响关系分批解析；完成前保持 pending，但当前授权立即 deny。
6. **未来消费者不造假：** conformance fixtures 证明协议，不证明 task/export/App 业务已经处理。
7. **跨模块只走事件/公开 API：** identity-access 不写 task、reporting、subject-registry 或 mobile 私有表。
8. **无明文与无持久客户端授权投影：** telemetry/event/audit 使用受控 token/digest；客户端缓存不能成为授权证据。
9. **授权消费者语义唯一：** `authorization-current-scope` 是本模块异步 fence/read-model consumer；动态 source/current 查询证明即时失权，异步 fence 证明传播，完整 role/object/action/scope 决策仍归 1.7。

### 数据与并发实现提示

- 可使用数据库行锁/条件版本为每个 lineage 维护 current head，并在同事务分配下一 `aggregateVersion`；事务回滚必须同时回滚 head、版本、fact、outbox 与 audit。禁止单一全局计数器让某个 poison/gap 阻塞无关聚合。
- 不要把已有 V000006 `consumer_watermark`（source projection 消费进度）复用为失效消费者水位；两者语义和恢复路径不同。
- outbox row、delivery attempt 与 consumer apply record 使用稳定唯一键；至少覆盖 crash-before-send、send-before-mark、apply-before-ack 和 ack-response-lost 四个窗口。
- 数据库权限必须阻止 producer 直接写 consumer apply watermark，也必须阻止一个 consumer 代写另一个 consumer 的水位；完成协调器只能读取真实 ack/reconciliation 证据。
- PostgreSQL `READ COMMITTED` 下每条语句可见快照可能不同；并发正确性依赖显式条件更新/锁/唯一约束，不依赖先查后写。
- 删除/保留必须绑定 investigation/hold 与 lineage，不能删除仍被 current head、未完成 propagation、gap/backfill 或 audit 调查引用的证据。

### UX、会话与错误语义

- 本 Story 不要求新增业务页面。若暴露运维/管理状态，必须区分 loading、真实空状态、筛选无结果、error、no-permission、degraded 与 propagation pending。
- 无权限使用“当前职责范围不包含此对象；本次访问已记录”或批准后的等价统一文案，不暴露对象是否存在、旧责任人或敏感字段名。
- 状态不可只靠颜色；必须有文字/结构/可访问名称。Toast 不能代替可持续查询的 propagation/reconciliation 状态。
- 重认证可返回原目标，但若 scope 已失效仍进入统一拒绝；不得显示持久离线业务对象。

### 技术版本与最新官方资料

- 仓库当前基线是 JDK 25、Spring Boot 4.1.0、Spring JDBC、PostgreSQL 18.4、pgJDBC 42.7.12；本 Story 不需要新增依赖或升级版本。
- PostgreSQL 18 的 `READ COMMITTED` 每条命令获得新快照，故必须以数据库约束和条件写保证并发原子性。[PostgreSQL 18 SET TRANSACTION](https://www.postgresql.org/docs/18/sql-set-transaction.html)
- PostgreSQL 18.4 于 2026-05-14 发布并包含安全/缺陷修复；测试与 release evidence 固定到仓库已采用的 18.4。[PostgreSQL 18.4 Release Notes](https://www.postgresql.org/docs/release/18.4/)
- pgJDBC 42.7.12 包含 `channelBinding=require` 安全修复；保留仓库当前版本。[pgJDBC 42.7.12 Release](https://jdbc.postgresql.org/changelogs/2026-06-29-42.7.12-release/)
- CloudEvents 当前规范版本仍为 1.0.2，JSON Schema 使用 2020-12。[CloudEvents Specification](https://github.com/cloudevents/spec)；[JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12)
- Spring transaction abstraction 与 JDBC 事务边界沿用当前官方模式，不引入额外事务框架。[Spring Transaction Management](https://docs.spring.io/spring-framework/reference/data-access/transaction.html)
