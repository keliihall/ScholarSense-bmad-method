## Story

作为数据责任人，
我希望明确 P0/P1 数据口径、责任与依赖，
以便平台只在合同完整、证据真实、课表/校历切片有效且依赖映射稳定时发布数据源目录，为后续主体关联、质量门与住宿安全规则提供可信输入。

## 业务与交付价值

- 建立 17 个当前规划 P0/P1 源的唯一、版本化、可审计目录，终止“P1 数据”无 owner 占位和同一来源多套口径。
- 固定 11 个 `sourceId → dependencyId` 映射及用途隔离，让后续规则组合能 fail closed，而不会用一个 eligible 源替代缺失或熔断的 required 源。
- 交付 FR-20 所需的住宿、请假/实习、门禁、设备、有效课表与校历最小切片；不把成绩、论文、心理正文或网络内容扩大进 MVP。
- 让数据责任人看见 owner、schema、SLO、质量门、补数/对账、契约测试与证据状态；任何缺口都形成 `invalid/not-publishable`，不产生“已发布”假成功。

## Story 元数据与实施边界

- **显式依赖：** 仅 Story 1.1d。当前 `main@9ab3369` 已包含 PR #37/Story 1.9；Story 1.2 的真实学校门户/IdP/KMS 证据仍缺失，但不是本 Story 的开工依赖，也不得被本 Story 写成已通过。
- **需求所有权：** 本 Story 是 FR-9 owner、BR-12 contributor。2.2/2.3/2.4 继续拥有主体映射、批次质量与规则资格事实；3.4 继续拥有 FR-20 最终生产住宿安全闭环。
- **受控范围：** `DCC-1.0.0`、`QG-1.0.0`、`QRP-1.0.0`、17 个 `sourceId`、11 个 `dependencyId` 和 owner/SLO/硬门已冻结；本 Story 不重开 DEC-012，只负责物化合同、验证器、目录发布能力与真实证据 URI。
- **证据分母：** 静态规划文件、JSON fixture、mock source、HTTP 2xx 或本地 checker 只能证明合同/实现正确，不能替代逐源运行证据。目录可在非生产环境验证，但 `published` 必须绑定获准目标源产生的不可变证据；没有真实证据的版本保持 `invalid/not-publishable`。
- **模块所有权：** `ingestion-quality` 唯一拥有数据源目录版本、源合同登记、最小切片接入状态及后续 DataBatch/QualitySnapshot；其他模块只能经 `<module>.api` 或版本化事件读取。
- **状态边界：** 本 Story 不创建 `RuleEvaluation`、`CandidateAdmissionDecision`、`Candidate`、`Clue`、公共待办或 `QualityEligibility`。11 个 dependency 初始仍可为 `fused`；目录发布不等于质量 eligible、规则 production 或场景已通过。
- **发布模型：** `DCC-1.0.0` 是合同基线版本；一次目录发布必须另有 UUIDv7 `catalogReleaseId`、单调 `aggregateVersion`、内容摘要、`publishedAt` 和 evidence set，不允许覆盖基线文件或原位改写已发布版本。
- **估算校准：** 上游 `5d` 只覆盖目录主路径。当前仓库尚无 ingestion-quality 生产实现、迁移、DCC/QG 合同包或页面；加上 17 源/11 dependency、真实证据、首条 Epic 2 migration、发布清单 successor 与 Web 验收，建议 `8-12d`。若容量坚持 5d，应先 correct-course 拆分，不能删除证据、授权、迁移或最小切片门。

### 本 Story 包含

1. 17 源目录、11 dependency registry、DCC/QG schema/lock/fixtures/checker 和版本化发布状态。
2. FR-20 最小 P0 切片合同：住宿、请假/实习/离返校、校门/宿舍门禁、门禁设备、`BC-1.0.0` 校历与学生有效课程/教学活动时间窗。
3. R6 数据责任人授权下的目录查询、校验与发布；原子持久化业务结果、幂等结果和本地审计 outbox。
4. 逐源 provider/consumer contract test、补数/对账结果及不可变证据 URI；fixture 与真实证据分栏。
5. 数据源目录 Web 表面，明确发布/失效原因、owner、purpose、版本、SLO、质量门、证据与更新时间。
6. DCC/QG 受控输入进入 release manifest successor，并保持 v1/v2 文档与既有 digest 不变。

### 本 Story 不包含

- 17 个源的完整业务数据湖、全量 ETL、完整学业域、成绩/论文、心理诊断/咨询正文、网址/域名/报文内容。
- 主体映射修复/历史窗口重算（2.2）、DataBatch 状态机和质量快照计算（2.3）、RuleDependencyRegistry 组合资格事实（2.4）。
- 规则 canary/production、熔断恢复审批、RuleEvaluation、Candidate/Clue 或公共任务。
- 新建消息总线、缓存、数据编排产品或通用任务中心；不得把 provider/技术投递状态写进来源业务状态。
- 修改 `RFP-1.0.0` 的角色/动作语义；R6 已有 `data-quality.read/repair/reconcile` 与 `platform.read-source`，未知动作继续 deny。
- 将测试密钥、学校 endpoint、凭据、学生明文或原始证据正文提交到仓库。

## Acceptance Criteria

### AC-2.1-HAPPY：发布完整且稳定的数据源目录（受控原始 AC）

**Given** DEC-012 的 17 个 P0/P1 源分别具备具名 owner、schema、SLO、质量门、补数/对账、契约测试和 evidenceUri<br>
**When** 数据责任人发布目录版本<br>
**Then** 目录恰含 DEC-012 的 17 个当前规划源且 `sourceId` 全局唯一、稳定不复用；每个源保存 purpose、版本与责任，每个规则消费源映射稳定 `dependencyId`，非规则消费源明确用途隔离；任一必填缺失或契约不兼容时该目录版本标记 `invalid/not-publishable`<br>
**And** 交付 FR-20 所需的实习/请假、校外住宿、门禁/设备、有效课表与校历 P0 最小切片，且不得用 fixture 代替生产证据。

### AC-2.1-CATALOG-CONTRACT：17 源合同恰好完整且不可静默漂移

**Given** `DCC-1.0.0/QG-1.0.0` 合同包被构建、启动或发布流程加载<br>
**When** checker 校验目录、逐源 schema、SLO、质量门、补数/对账、owner、purpose、版本、生效区间、证据 URI 与 contract lock<br>
**Then** 当前发布集合必须恰有以下 17 个稳定 `sourceId`，缺一、多一、重复、大小写变体或复用退役 ID 均失败关闭：

`SRC-P0-STUDENT-001`、`SRC-P0-RESPONSIBILITY-001`、`SRC-P0-ACCOMMODATION-001`、`SRC-P0-CARD-001`、`SRC-P0-CAMPUS-ACCESS-001`、`SRC-P0-DORM-ACCESS-001`、`SRC-P0-DEVICE-001`、`SRC-P0-LEAVE-001`、`SRC-P0-CALENDAR-001`、`SRC-P0-TIMETABLE-001`、`SRC-P1-OFFCAMPUS-001`、`SRC-P1-NETWORK-001`、`SRC-P1-ACADEMIC-001`、`SRC-P1-CARE-LIST-001`、`SRC-P1-PSYCH-DEID-001`、`SRC-P1-AID-001`、`SRC-P1-WORK-VISIT-001`<br>
**And** 每个 descriptor 至少登记责任部门/具名 owner、业务定义与 purpose、业务主键/有效区间、更新频率/SLO、覆盖范围、敏感分类、schema/质量门/对账/补数与证据合同；不允许仅以技术系统名或“P1 数据”占位<br>
**And** 共同硬门必须机器可验证：schema allowlist/兼容率 `100%`、禁止字段 `0`、进入计算记录 required-field validity `100%`、全源有效记录率 `>=99.5%`、P0 主体映射 `>=99.5%`、核心字段 `>=98%`、SLO 内到达 `>=99%`，未解决区间冲突/重复业务键/版本倒退均为 `0`；逐源更严门槛仍以 QG-1.0.0 为准<br>
**And** schema 只允许向后兼容新增 optional 字段；删除/改义/收窄/新增 required 字段必须产生新 major/新受控目录版本和兼容窗口，不能改写同版本 digest。

### AC-2.1-DEPENDENCY-MAPPING：11 个规则依赖稳定且用途隔离

**Given** 规则目录 RC-1.0.0 和 DCC 目录均通过静态验证<br>
**When** 构建 `sourceId → dependencyId` registry<br>
**Then** 必须恰好包含以下 11 个稳定映射：

- `SRC-P0-CAMPUS-ACCESS-001 → DEP-P0-CAMPUS-ACCESS-001`
- `SRC-P0-DORM-ACCESS-001 → DEP-P0-DORM-ACCESS-001`
- `SRC-P0-ACCOMMODATION-001 → DEP-P0-ACCOMMODATION-001`
- `SRC-P0-LEAVE-001 → DEP-P0-LEAVE-001`
- `SRC-P0-CALENDAR-001 → DEP-P0-CALENDAR-001`
- `SRC-P0-CARD-001 → DEP-P0-CONSUMPTION-001`
- `SRC-P0-TIMETABLE-001 → DEP-P0-TIMETABLE-001`
- `SRC-P0-DEVICE-001 → DEP-P0-DEVICE-001`
- `SRC-P1-OFFCAMPUS-001 → DEP-P1-OFFCAMPUS-001`
- `SRC-P1-NETWORK-001 → DEP-P1-NETWORK-001`
- `SRC-P1-ACADEMIC-001 → DEP-P1-ACADEMIC-001`

**And** STUDENT、RESPONSIBILITY、CARE-LIST、PSYCH-DEID、AID、WORK-VISIT 等非规则直连/治理源保留稳定 `sourceId + purpose` 合同，不伪造 dependency；本 Story 只登记 `required/optional + all-of|any-of|threshold` 声明，不提前发布组合 `QualityEligibility`。

### AC-2.1-MINIMAL-SLICES：课表、校历与 FR-20 排除输入最小化且可重现

**Given** 住宿安全所需来源合同 approved/effective<br>
**When** 验证最小切片及边界样本<br>
**Then** `SRC-P0-CALENDAR-001` 必须引用 `BC-1.0.0`、`Asia/Shanghai`，覆盖 `today-90d..today+180d` 且每个 `[00:00,next 00:00)` 自然日恰一 `dayType`；值只允许 `workday|weekend|statutory-holiday|makeup-workday|school-holiday|emergency-closure`，并包含适用区间、生效/更正版本；缺日、重叠版本或未知 dayType 失败关闭<br>
**And** `SRC-P0-TIMETABLE-001` 只含学生/学期/教学班、活动起止、校区/地点、选课有效、停调课/取消、`effectiveAt`、`sourceUpdatedAt`、源版本、水位与更正链；不含成绩、排名、论文或完整教务档案<br>
**And** 住宿、请假/实习/离返校、校外住宿、校门/宿舍门禁和设备区间合同能在相同源版本/时间语义下复现 FR-20 的排除判断；所有时间存 UTC、接口带 offset、业务解释使用 `Asia/Shanghai`。

### AC-2.1-INVALID-NOT-PUBLISHABLE：不完整或不兼容目录不能成为 current

**Given** 任一源缺 owner/schema/SLO/qualityGateVersion/reconciliation/contract-test/evidence，或 source/dependency 重复、版本倒退、schema 不兼容、校历有缺口/重叠、课表包含禁止字段<br>
**When** 数据责任人校验或发布目录<br>
**Then** 服务端持久化可解释的 `invalid/not-publishable` 结果、稳定错误码和字段路径，current published 指针保持原版本；不得部分发布 16/17 源、不得自动降门槛、不得把 fixture URI 提升成 runtime evidence<br>
**And** 修复必须创建新校验尝试/新 aggregateVersion；已发布版本与其 digest、证据集合和审计历史不可改写。

### AC-2.1-AUTH-AUDIT：目录读写按 R6 ownerBinding 授权并原子审计

**Given** RFP-1.0.0 当前授权上下文与 ownerBinding 可用<br>
**When** R6 数据责任人读取 owned source、执行校验/对账或发布目录，或其他角色/越 scope 调用同一接口<br>
**Then** 服务端逐请求执行对象/动作/scope 授权；R6 仅可操作 owned source/dependency，越权与对象不存在使用同一不泄露语义，R7 默认只见技术状态<br>
**And** 发布命令携带 `Idempotency-Key + expected aggregateVersion`；同键同摘要重放原响应、同键异摘要或旧版本返回 409；目录、幂等结果和 `LocalAuditFact` outbox 在同一事务提交，审计失败则发布失败。

### AC-2.1-EVIDENCE-TRUTH：真实证据与 fixture 明确分栏

**Given** 合同测试同时存在本地 fixtures 和获准目标源运行<br>
**When** 生成逐源 evidence set 与目录 `evidenceUri`<br>
**Then** 每条证据绑定 sourceId、contract/schema/qualityGate 版本、目标环境/authority、候选 commit/tree、输入摘要、测试场景、结果、发生时间、签名/不可变摘要和清理结果；URI 指向不可变对象，不能只指回规划文档<br>
**And** fixture/mock/local evidence 明确 `runtimeEvidenceClaim=none`；任一真实逐源场景 failed/skipped/unsupported、证据签名/摘要/subject 不匹配或含个人明文时，目录保持 not-publishable。

### AC-2.1-UX：数据责任人可访问地理解目录与失败原因

**Given** R6 进入数据源目录表面<br>
**When** 查看列表、源详情、版本或发布结果<br>
**Then** 页面显示 sourceId、dependencyId（如适用）、责任部门/owner、业务定义/purpose、业务主键、更新频率、覆盖范围、schema/合同版本、SLO、质量门、补数/对账、evidence 状态、更新时间与 publishability；空、筛选无结果、错误、无权、陈旧和 invalid 分开表达<br>
**And** 状态使用文字+语义图标，不只靠颜色；表格支持键盘、焦点、错误摘要和 200% 缩放；R7 技术表面不得出现学生明细、证据正文或 owner scope 外内容。

1. 先锁合同、exact sets、错误和负例，再写领域/持久化/UI；禁止从代码反推 DCC。
